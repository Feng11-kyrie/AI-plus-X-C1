# 拿来说明 03：把「覆盖 80%」从一个说法变成一个可核对的数字

> **一句话**：挑战要求覆盖 80% 的讲义/字幕。
> 但**分母是什么**没人定义过。而这个定义直接决定了一件事——
> 只翻 HTML 是 **76.5%**（不达标），纳入 3 份 PDF 才是 **85.3%**（达标）。

---

## 一、原文（输入）

课程大纲里一共登记了 **44 条 readings**。它们长这样（摘自 `source/index.html` 解析结果）：

```json
{
  "week": 1,
  "readings": [
    {"text": "Deep Dive into LLMs",            "url": "https://www.youtube.com/watch?v=7xTGNNLPyMI"},
    {"text": "Prompt Engineering Overview",     "url": "pages/prompt-engineering-overview.html"},
    {"text": "Prompt Engineering Guide",        "url": "pages/prompt-engineering-guide.html"},
    {"text": "AI Prompt Engineering: A Deep Dive","url": "https://www.youtube.com/watch?v=T9aRN5JkmL8"},
    {"text": "How OpenAI Uses Codex",           "url": "pdfs/how-openai-uses-codex.pdf"}
  ]
}
```

一眼看去，44 条就是分母，覆盖率 = 已翻译 / 44。

**这个算法是错的**，而且错得不容易发现——因为 44 这个数字看起来完全合理。

---

## 二、prompt（怎么让 AI 做的）

我没有直接让 AI「统计有多少条 readings」，而是让它先回答一个更基础的问题：

> **「这 44 条里，哪些是真的有本地文件的？哪些只是指向外部站点？」**
>
> 然后进一步问：**「有本地文件的那些，文件里真的有内容吗？」**

这两个追问把 44 拆成了三层：

```
44 条 readings
 ├─ 10 条指向外部站点（YouTube / GitHub / X / 第三方博客）——不受本项目控制
 └─ 34 条指向本地文件
     ├─ 32 条文件里有内容 ──┐
     └─  2 条文件是空的/占位 ┘ 但清洗后发现实际是 5 条
```

第三层追问是关键的：「**有文件**」和「**文件里有内容**」是两回事。

---

## 三、产出（AI 给出的）

### 3.1 分母的正式定义（固化进代码）

`pipeline/inventory.py` 里把定义写死：

```python
# 分母 = 大纲中指向本地文件的 readings = 34 条
local   = [u for u in units if u["kind"] == "local"]
usable  = [u for u in local if u["status"] == "ok"]
target  = CFG["coverage"]["target_ratio"]          # 0.8
need    = -(-int(len(local) * target))             # ceil(34 × 0.8) = 27
```

`source/INVENTORY.md` 里明确写出：

> - **分母 = 大纲中指向本地文件的 readings = 34 条**
> - 其中可用 = 29 条（HTML 26 + PDF 3），确认无效 = 5 条
> - 目标：分子 / 分母 ≥ **80%**，即 ≥ 27 条
>
> **为什么不把外链算进分母**：它们不受本地缓存控制，其可获得性取决于对方站点
> 与账号权限，属于扩展范围。计入分母会让覆盖率失去可比性。

### 3.2 意外收获：分母定义暴露了 3 个隐形缺口

追查「文件里有内容吗」时，清洗管线发现失效的不是原缓存 README 声称的 2 条，而是 **5 条**：

| # | 篇目 | 症状 | 失效模式 |
|---|---|---|---|
| 1 | `prompt-engineering-guide` | 128KB 但正文仅 548 字节 | **SPA 导航壳**：`__NEXT_DATA__` 载荷为空，真实正文在未被抓取的子页面 |
| 2 | `good-context-good-code` | 9KB 但正文仅 77 字节 | **付费墙**：抓到的是登录门页 |
| 3 | `peeking-under-the-hood-of-claude-code` | 550 字节 | 反爬占位页（源站 Medium） |
| 4 | `how-warp-uses-warp` | 15KB 但正文仅 7 字节 | **Notion JS 渲染页**：静态抓取只有外壳 |
| 5 | `lessons-from-ai-code-reviews` | **0 字节** | 抓取完全失败 |

原缓存自带的 README **只承认了第 3 条和第 5 条**。前三条是这次追问才发现的。

### 3.3 最重要的产出：一个可行性结论

```python
usable_html = 26      # 可用 HTML 条目
usable_pdf  = 3       # 可用 PDF 条目
local       = 34      # 分母
need        = 27      # 达 80% 所需

26 / 34 = 76.5%   ← 只翻 HTML：不达标 ❌
29 / 34 = 85.3%   ← 纳入 PDF：达标 ✅
```

**结论：3 份 PDF 从「可选」变成了「必须纳入」。**

这个结论只有在分母定义清楚之后才能得出。如果分母含糊，最可能的结果是：

- 翻了 26 篇 HTML
- 自认为做得不错（26 篇，不少了）
- 交付时才发现 26/34 = 76.5%，**不达标**
- 而此时已经投入了大量翻译工作量

**分母不是统计口径问题，它是任务边界问题。**

## 四、对比

### 4.1 三种分母口径下的覆盖率

| 分母定义 | 分母 | 全部译完的覆盖率 | 判断 |
|---|---|---|---|
| 全部 readings | 44 | 29/44 = 65.9% | ❌ 永远不达标（外链拿不到） |
| 本地文件条目（**采用**） | 34 | 29/34 = **85.3%** | ✅ 达标 |
| 只算 HTML | 31 | 26/31 = 83.9% | ✅ 但漏了 PDF，实际交付物不完整 |

**同一个项目，换一个分母，结论从"永远不达标"变成"达标"。**

这就是为什么挑战要求在 README 里写"覆盖范围与已知缺口"——**分母必须公开，否则无法核对。**

### 4.2 分母定义带来的连锁影响

| 影响 | 说明 |
|---|---|
| **PDF 变成必做项** | 只翻 HTML 是 76.5%，低于目标 |
| **清洗管线必须支持 PDF** | 原本只处理 HTML，为此新增了 `pdfkit_dump.js`（提取 106,039 字符） |
| **失效条目要如实登记** | 5 条失效占分母的比例不能隐瞒，否则覆盖率是自欺 |
| **扩展范围要单列** | 10 条外链 + 讲义 + 视频字幕，写进 INVENTORY.md 而不是悄悄忽略 |

### 4.3 「已知缺口」是加分项而不是减分项

我最初的本能是：**缺口写得越少越好，免得被扣分。**

实际情况相反。逐条列出 5 个失效条目、每个都说明失效模式与处置建议，同时命中了 rubric 的两条：

- `artifactCompleteness` 的「README 齐全」——因为缺口是资料包说明的必要组成部分
- `reflectionQuality` 的「具体问题分析」——因为每个缺口都配了成因分析

**含糊带过才是扣分项。**

## 五、沉淀

### 5.1 一条可复制的做法

> **任何百分比，交付前先写清楚分母是什么、为什么这么定、以及换了分母结论会不会变。**

具体到本项目，这条做法落地成了三个可核对的东西：

1. **分母定义写进代码**（`inventory.py`），不是写在文档里靠人记
2. **覆盖率报告自动生成**（`reports/coverage.md`），分子分母都实时可见
3. **换个分母会怎样，明确列出来**（见 4.1 的三行对比）

### 5.2 一个判断原则

**分母应该由"我能控制什么"来划定，而不是由"名义上有多少"来划定。**

- 外链指向 YouTube / GitHub —— 我控制不了它会不会失效、要不要账号，**不计入**
- 讲义是 Google Slides —— 需要 Google 账号，自动化不可行，**不计入分母，单列为扩展范围**
- 本地文件 —— 我控制得了它有没有内容，**计入**

这不是为了把数字做好看（把 10 条外链计入反而会让覆盖率永远达不到 80%，是自伤）。**而是为了让这个数字有意义——能被核对，也能指导决策。**

### 5.3 最有价值的一步：「有文件」≠「文件里有内容」

34 条本地条目里，有 5 条是"看起来有、实际没有"：

| 表面现象 | 实际情况 |
|---|---|
| `prompt-engineering-guide.html` 128KB | 正文 548 字节，其余是导航壳 |
| `how-warp-uses-warp.html` 15KB | 正文 7 字节，Notion 的 JS 外壳 |
| `lessons-from-ai-code-reviews.html` 有文件名 | 0 字节 |

**如果只在文件系统层面统计（文件存不存在、多大），这 5 条全都会被算作"已获取"。**

必须真的把内容提取出来、量一量，才知道哪些是空壳。这也是为什么清洗步骤必须做在清点之前——**否则清点就是在数文件名。**
