# 拿来说明 01：清洗管线为什么静默丢掉了 9,156 字符正文

> **一句话**：我断言「清洗质量很高」，实际有 4 个静默丢内容的 bug。
> 转折点不是某个 bug 的发现，而是我意识到**管线里没有任何机制能替我发现自己看漏了**。

---

## 一、原文（输入）

清洗管线 `pipeline/clean.py` 的第一版把 `<figure>` 放进了样板剔除集合：

```python
# 第一版（commit 8cd9a7a 之前）
BOILERPLATE = {
    "script", "style", "noscript", "nav", "header", "footer", "aside",
    "form", "iframe", "svg", "button", "select", "option", "template",
    "figure", "video", "audio", "canvas", "map", "object", "embed",
}
```

理由是：`<figure>` 通常是图片容器，属于版面元素而非正文。

而源文件里的实际情况是这样的（`source/pages/mcp-server-authentication.html` 原文片段）：

```html
<figure class="frame code-output not-content">
  <figcaption class="header"></figcaption>
  <pre data-language="sh"><code>
    <div class="ec-line"><div class="code">
      <span>Starting</span><span> </span><span>local</span><span> </span><span>server...</span>
    </div></div>
  </code></pre>
</figure>
```

**`<figure>` 里装的是代码块。** 这是 Astro Starlight / Expressive Code 框架的标准输出结构——它把 `<pre><code>` 包进 `<figure class="frame code-output">` 以获得更好的样式控制。

一个佐证：那个 class 里甚至写着 `not-content`，看上去像是在主动声明"我不是正文"。**但它的子节点是货真价实的正文。**

---

## 二、prompt（怎么让 AI 做的）

第一轮清洗跑通后，我（作为执行 agent）抽检了一篇输出——`sast-vs-dast.md`——看到标题层级、链接、代码块、表格全部正确，便得出了**「清洗质量很高」**的结论。

这个结论是错误的。推翻它的问题不是我主动问出来的，而是**人在复核时提出了一个我没想到的角度**：

> 「你认为第一步还需要改善什么」

被要求系统自查后，我做的第一件事是**逐篇统计原始 HTML 里各类元素的数量，而不是继续看输出**：

```
检查 1：<figure> 被整棵剔除 —— 是否误删了正文？
  agentic-ai-threats                           figure 21 个，其中含正文块 0 个
  code-reviews-just-do-it                      figure  8 个，其中含正文块 0 个
  context-rot                                  figure 58 个，其中含正文块 14 个
  mcp-introduction                             figure  1 个，其中含正文块 0 个
  mcp-server-authentication                    figure 21 个，其中含正文块 20 个
  specs-are-the-new-source-code                figure  4 个，其中含正文块 0 个
  writing-effective-tools-for-agents           figure  8 个，其中含正文块 1 个
```

**关键设计**：这个检查问的不是"输出看起来对不对"，而是"原文里有多少东西，输出里还剩多少"。**换了一个提问方向，问题就自己浮出来了。**

## 三、产出（AI 给出的）

### 3.1 损失量化

| 篇目 | `<figure>` 数 | 其中含正文 | 丢弃字符（去空白口径） |
|---|---|---|---|
| `context-rot` | 58 | 14 | **6,961** |
| `mcp-server-authentication` | 21 | 20 | **1,452** |
| `writing-effective-tools-for-agents` | 8 | 1 | **743** |
| **合计** | 87 | 35 | **9,156** |

> 口径说明：把每个 `<figure>` 子树内的文字提取出来、去掉全部空白字符后求和。
> 若计入空格则为 10,735 字符。

### 3.2 修复

```python
# 现在
BOILERPLATE = {
    "script", "style", "noscript", "nav", "header", "footer", "aside",
    "form", "iframe", "svg", "button", "select", "option", "template",
    "video", "audio", "canvas", "map", "object", "embed",
}   # figure 已移出
```

配套改动：`render()` 里为 `figcaption` 单独分支，把它渲染成斜体图注——既不与正文混淆，也不丢失信息。

### 3.3 更重要的产出：一个能自动发现这类问题的校验器

修完这一个 bug 之后，我没有停下来，而是补上了**本可以一开始就防止它发生的机制**：

`clean.py` 现在对每篇比对三个层次的元素数量：

| 层次 | 含义 |
|---|---|
| `raw` | 整个原始文件（含样板） |
| `main` | 剔除样板、选定正文容器之后 |
| `md` | 最终 Markdown |

- `raw → main` 的差距 → **样板剔除误伤正文**（`figure` bug 属于此类）
- `main → md` 的差距 → **渲染器漏渲染**
- **文字留存率**（正文文字 → Markdown 纯文字）是主判据，低于 90% 报警
- 代码块单独严判：丢了围栏就会被当散文翻译，而代码必须逐字保留

**这个校验器上线后，立刻又抓出 3 个我原本不知道的 bug：**

| # | Bug | 损失 | 体积指标能看到吗 |
|---|---|---|---|
| 2 | `_list()` 兜底分支把块级子元素扁平化 | 17 个代码块丢围栏 | ❌ |
| 3 | `_table()` 在 `rows<2` 时整表丢弃 | 1 篇丢 5,608 字符 | ❌ |
| 4 | 表格单元格里的代码块被压成纯文本 | 1 个代码块失效 | ❌ |

## 四、对比

### 4.1 修复前后（同一条目）

```
context-rot                    42,883 字符 → 51,207 字符   (+19.4%)
mcp-server-authentication      12,740 字符 → 14,608 字符   (+14.7%)
```

### 4.2 我的判断 vs 实际

| | 我的结论 | 实际 |
|---|---|---|
| 依据 | 抽检 1 篇（`sast-vs-dast`，恰好不含 `<figure>`） | 全量元素计数 |
| 结论 | 「清洗质量很高」 | 4 个静默丢内容 bug |
| 后果 | 若就此进入翻译，26 篇中有 3 篇内容残缺且**无人知晓** | 已在翻译开始前修复 |

### 4.3 为什么体积指标完全看不出来

这是本案例最值得记的一点：

- `context-rot` 丢失 6,961 字符后，产物仍然有 42,883 字符——**看起来完全正常**
- `mcp-server-authentication` 丢了 20 个代码块中的内容，产物仍有 12,740 字符
- 文件大小、段落数、标题数都在合理范围

**一个只测"体积"的管线，对静默丢内容是完全瞎的。** 这是本次最关键的方法论认识。

## 五、沉淀

### 5.1 一条具体的教训：分类依据错了

我把 `<figure>` 归入样板，依据是「它通常是什么」——图片容器。

正确的依据应该是**「它包含什么」**。同样是 `<figure>`：

- 包着 `<img>` 的 → 可以剔除
- 包着 `<pre><code>` 的 → 是正文，必须保留

**按"通常是什么"分类，在遇到框架自定义用法时必然出错。** 修复方式不是逐个枚举特例，而是改成按内容判定（保留 `figure`、递归渲染内部、只对 `figcaption` 特殊处理）。

### 5.2 一条可复制的方法：换个提问方向

- ❌ 「输出看起来对吗？」→ 抽样式信任，样本量为 1 时几乎必然漏检
- ✅ 「原文里有多少，输出里还剩多少？」→ 穷举式信任，差值自动暴露问题

同一个管线、同一批数据，**只是换了提问方向，问题就从"看不见"变成"自己跳出来"。**

### 5.3 一条更根本的教训：先建守卫，再建功能

我原本的顺序是「先把清洗做出来 → 抽检确认没问题 → 进入下一步」。

正确的顺序是「**先把校验建起来 → 再让功能跑**」。

因为功能的第一版几乎一定有 bug，而**没有守卫的情况下，你无法知道自己有没有 bug**——只能靠抽样，而抽样会骗你。
