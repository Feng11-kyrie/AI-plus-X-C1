# 拿来说明 02：术语校验器的 17 次拦截，其中 6 次才是我真错了

> **一句话**：我把术语表写进了 prompt，然后 36 块译文里被机械校验拦下 17 次术语违规。
> 但真正有价值的不只是"拦住了我的错"，而是**分析这 17 次之后发现：机器判错的次数比我还多。**

---

## 一、原文（输入）

翻译管线的 prompt 里，术语表是**按块注入**的——只注入该块实际命中的术语，避免把 171 条塞进每个 prompt：

```
你是资深技术文档译者。把下面的英文 Markdown 译成简体中文。

硬性要求：
1. 完整保留 Markdown 结构：标题层级、列表、表格、引用、链接、代码块围栏。
2. 代码块内容逐字保留，绝不翻译，包括其中的注释与标识符。
3. 链接与图片的 URL 一字不改，只翻译可见文字。
4. 术语必须严格使用下表给定译法；禁用变体一律不得出现。
5. 不增、不删、不加译者注、不加任何解释或前后缀。
6. 只输出译文本身。

术语表（必须遵守）：

| 英文 | 中文 | 禁用变体 |
|---|---|---|
| Agent | 智能体 | 代理、智能代理、代理人、Agent 体 |
| Agentic | 智能体化的 | 代理式、自治式、Agent 化 |
| Coding Agent | 编码智能体 | 编程代理、代码智能体、编码代理 |
| Orchestration | 编排 | 协调、编排调度、组织 |
| Terminal | 终端 | 命令行窗口、控制台 |
| ...（该块命中的其余术语） |
```

注意第 4 条：**「禁用变体一律不得出现」**。这条规则是明确的、可执行的、写在 prompt 里的。

而译文里实际出现的违规是：

```
出现禁用变体「协调」（应为「编排」）
```

**「协调」就明明白白印在那个 prompt 的禁用变体列里。** 我读了、照抄了、还是写错了。

---

## 二、prompt（怎么让 AI 做的）

除了翻译 prompt 本身，真正起作用的是**第二个 prompt**——写给校验器的规则：

> 逐块机械校验以下四项：
> 1. 代码围栏数必须与原文一致
> 2. 链接数必须与原文一致
> 3. **术语表声明的禁用变体一律不得出现**
> 4. 中英字符比在合理区间（低于 0.25 疑漏译，高于 2.0 疑添加内容）
>
> 任一项不通过 → 该块判为不通过，必须返工。

**关键设计：这个校验不是我"看一眼"，而是一段代码在每次收回译文时自动跑。** 它不接受"我觉得没问题"，只接受字符串匹配结果。

### 3.3 由此产生的三处修复

**修复一：包含关系判定**（消除 5 次误报）

```python
def variant_hits(zh: str, term: dict) -> tuple:
    approved = (term.get("term_zh") or "").strip()
    for key, bucket in (("forbidden_zh", hard), ("forbidden_soft", soft)):
        for fb in filter(None, (x.strip() for x in (term.get(key) or "").split("|"))):
            if approved and fb in approved:
                continue          # 被正式译法包含 → 必然误报，跳过
            if fb in zh:
                bucket.append(...)
```

**修复二：硬性/提示两级**（处理 3 次规则过宽）

术语表新增 `forbidden_soft` 列：

| 列 | 等级 | 校验行为 |
|---|---|---|
| `forbidden_zh` | **硬性** | 出现即判该块不通过，必须返工 |
| `forbidden_soft` | 提示级 | 只记录不拦截 |

**修复三：改术语表而不是改译文**（处理 1 次术语表错误）

新增 `Threat Modeling → 威胁建模` 词条；`Threat Model` 的禁用变体只留「风险模型」。

并在术语表校验器里新增 **R8 规则**：提示级变体若是正式译法的子串，说明它会被包含关系判定跳过，标记毫无意义——这条新规则立刻又抓出一处冗余（`Incident` 的「事件」「故障」）。

## 四、对比

### 4.1 同一个约定，两种实现方式的效力

| 实现方式 | 效力 |
|---|---|
| 写进 prompt（「禁用变体一律不得出现」） | 36 块里违反 **17 次** |
| 写成校验代码（字符串匹配 + 判不通过） | 违反 → **100% 被拦下，必须返工** |

**同一个约定，从"一句请求"变成"一段代码"，效力差了一个量级。**

### 4.2 修规则前后

| | 修复前 | 修复后 |
|---|---|---|
| 误报次数 | 5 + 3 + 1 = 9 | 0 |
| 规则准确率 | 6/17 ≈ 35% | 剩余命中均为真违规 |
| 我对校验器的信任 | 每次都要人工判断 | 可直接作为门禁 |

### 4.3 一个反例参照

修复过程中我**刻意没有放宽**「协调」这条规则。

理由：它第一次拦截就是真违规（我把 `orchestration` 译成了「协调」）。后来那 4 次虽然原文是 `coordinating`（协同），但这说明的是**规则与原文的对齐问题，不是规则本身错了**。

处置方式：**保留规则，改译文用词**——中文里「协同」完全够用。为了迁就一处误伤而放松一条已经证明有效的约束，是得不偿失的。

这个局限我如实记在了提交信息里：校验器只看中文输出，无法区分「协调」对应的是 orchestration 还是 coordination。彻底解决需要对齐原文，但会把校验器复杂化。**当前选择：接受一定误报，用人判断。**

## 五、沉淀

### 5.1 核心结论

> **术语一致性必须靠机制，不能靠自觉。**
>
> 证据：6 次真违规全部发生在我逐字读过术语表、且术语表已注入 prompt 的情况下。
> 其中最典型的一次，「协调」就印在 prompt 的禁用变体列里，我照抄着还是写错了。

### 5.2 更重要的一条：校验规则本身也需要被校验

17 次拦截里，**只有 6 次是我错了**。剩下 11 次是规则的问题。

如果我把校验器当成权威、不加分析地全盘接受，我会：

- 把「模型上下文协议（MCP）」改成违规写法
- 为了避开「记录」而不敢写"记录每一步"
- 把正确的「威胁建模」改成别扭的「威胁模型」

**一个天天误报的校验器最终会被人忽略——那才是真正的失效。**

### 5.3 人机分工的边界

| 谁 | 负责什么 | 为什么 |
|---|---|---|
| **机器** | 判断「符合不符合规则」 | 272 个块，人看不过来；机器不会疲劳 |
| **人** | 判断「规则对不对」 | 只有人能知道"这次是规则自己错了" |

**让机器判断前者是效率，让机器判断后者是灾难。**

### 5.4 一条工程实践

规则被实战推翻时，**改规则，但要把"为什么改"写进代码注释和提交信息**。

例如 `forbidden_soft` 列的引入理由，我写在了 `glossary_tool.py` 的注释里：

> 像「记录」「流程」这种词在中文里本身就常用（"记录每一步"、"排障流程"），
> 把它们一律判为违规会逼着人写出不自然的译文。

否则下一个维护者只会看到一堆 `soft` 标记，不明白为什么有的规则"比较松"。
