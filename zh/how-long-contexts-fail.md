### 管好上下文，是智能体成功的关键

随着前沿模型的上下文窗口持续增大¹——许多已支持到 100 万 Token——我看到大量兴奋的讨论，认为超长上下文窗口将解锁我们梦寐以求的智能体。毕竟窗口足够大时，你只需把可能需要的*一切*——工具、文档、指令等等——统统塞进提示词，剩下的交给模型就好。

长上下文浇灭了检索增强生成（RAG）的热潮（既然能全塞进提示词，何必再去找最合适的那篇文档！），助推了 MCP 的炒作（连上所有工具，模型就能干任何活！），也点燃了对智能体的热情²。

但现实是，**更长的上下文并不会带来更好的回答**。把上下文塞得过满，会让你的智能体与应用以意想不到的方式失败。上下文可能被毒化、被干扰、被混淆，或自相冲突。这对智能体尤其棘手——它们正是靠上下文来收集信息、综合结论并协调行动的。

下面我们逐一梳理上下文失控的方式，然后再看缓解乃至彻底避免上下文失败的方法。

## 上下文的失效方式

- **上下文毒化**：幻觉进入了上下文
- **上下文干扰**：上下文压过了训练所学
- **上下文混淆**：多余的上下文影响了回答
- **上下文冲突**：上下文各部分互相矛盾

### 上下文毒化

*上下文毒化，是指幻觉或其他错误进入上下文后，被反复引用。*

DeepMind 团队在 [Gemini 2.5 技术报告](https://storage.googleapis.com/deepmind-media/gemini/gemini_v2_5_report.pdf)中点出了上下文毒化问题，[我们上周做过解读](https://www.dbreunig.com/2025/06/17/an-agentic-case-study-playing-pokémon-with-gemini.html)。在玩宝可梦时，Gemini 智能体偶尔会产生幻觉，从而毒化自己的上下文：

> 这类问题有一种尤其严重的形态叫「上下文毒化」——上下文的许多部分（目标、摘要）被关于游戏状态的错误信息「毒化」，往往要很久才能纠正过来。结果是，模型可能执迷于达成不可能或不相关的目标。

如果上下文中「目标」这一部分被毒化，智能体就会发展出荒唐的策略，为追逐一个无法达成的目标而重复某些行为。

### 上下文干扰

*上下文干扰，是指上下文变得过长，模型过度关注上下文，反而忽略了训练时学到的东西。*

在智能体工作流中，随着上下文增长——模型收集到更多信息、积累了更多历史——这些累积的上下文可能从有帮助变成干扰。那只会玩宝可梦的 Gemini 智能体清楚地展示了这个问题：

> 虽然 Gemini 2.5 Pro 支持 100 万 Token 以上的上下文，但要让智能体有效利用它，仍是一片新的研究前沿。在这个智能体设定中观察到，当上下文显著超过 100k Token 后，智能体表现出倾向于重复其庞大历史中的动作，而不是综合出新的方案。这一现象虽属轶事性观察，却凸显了一个重要区别：用于检索的长上下文，与用于多步生成式推理的长上下文，并不是一回事。

智能体没有运用训练所得去发展新策略，而是执迷于重复其上下文历史中的过往动作。

对较小的模型而言，干扰的天花板要低得多。一项 [Databricks 研究](https://www.databricks.com/blog/long-context-rag-performance-llms)发现，Llama 3.1 405b 的正确率大约在 32k 处开始下滑，更小的模型则更早。

如果模型在上下文窗口被填满之前很久就开始失常，那超大的上下文窗口意义何在？简而言之：**摘要生成³与事实检索**。如果你不做这两件事，就要警惕所选模型的干扰天花板。

### 上下文混淆

*上下文混淆，是指模型把上下文中多余的内容用于生成低质量回答。*

有一阵子，看起来*所有人*都要发布一个 [MCP](https://www.dbreunig.com/2025/03/18/mcps-are-apis-for-llms.html) 了。一个强大的模型连上你*所有*的服务和*东西*、替你干完所有琐事——这个梦想仿佛近在咫尺。只要把所有工具描述塞进提示词，然后按下去就行了。[Claude 的系统提示词](https://www.dbreunig.com/2025/05/07/claude-s-system-prompt-chatbots-are-more-than-just-models.html)给我们指了路——它大部分内容就是工具定义或工具使用说明。

但即便[整合与竞争没有拖慢 MCP 的脚步](https://www.dbreunig.com/2025/06/16/drawbridges-go-up.html)，*上下文混淆*也会。事实证明，工具太多确实会出问题。

[伯克利函数调用排行榜](https://gorilla.cs.berkeley.edu/leaderboard.html)是一个工具调用基准测试，用于评估模型有效使用工具回应提示词的能力。如今已到第三版，该榜单显示：**当提供的工具多于一个时，*每一个*模型的表现都会变差⁴**。更进一步，伯克利团队「设计了一些场景，其中提供的函数全都不相关……我们期望模型的输出是不调用任何函数。」然而，所有模型偶尔仍会调用不相关的工具。

浏览这个函数调用榜单，你会看到问题随模型变小而加剧：

![](/img/gemma_irrelevance.png)

上下文混淆的一个突出例子见于[近期一篇论文](https://arxiv.org/pdf/2411.15399?)，该论文在 [GeoEngine 基准测试](https://arxiv.org/abs/2404.15500)上评估小模型表现——这个测试包含*46 个不同的工具*。当团队把一个量化（压缩）过的 Llama 3.1 8b 连同全部 46 个工具一起给出去时，它失败了，尽管上下文远在 16k 窗口之内。而当他们只给模型 19 个工具时，它成功了。

问题在于：**只要你把某样东西放进上下文，模型就必须关注它。** 它可能是不相关的信息或无用的工具定义，但模型*一定*会把它考虑进去。大模型，尤其是推理模型，正越来越擅长忽略或丢弃多余的上下文，但我们仍不断看到无价值的信息绊倒智能体。更长的上下文让我们能塞进更多信息，但这项能力是有代价的。

### 上下文冲突

*上下文冲突，是指上下文中累积的新信息与工具，与上下文中的其它信息相矛盾。*

这是*上下文混淆*更麻烦的一种形态：这里的坏上下文不是不相关，而是与提示词中的其它信息**直接冲突**。

Microsoft 与 Salesforce 的团队在[近期一篇论文](https://arxiv.org/pdf/2505.06120)中精彩地记录了这一点。该团队取来多个基准测试的提示词，把其中的信息「分片」到多轮提示中。可以这样理解：有时你会坐下来，在按下回车前把必要的细节一段段敲进 ChatGPT 或 Claude；另一些时候，你会先给一个简单提示，等回答不满意时再补上更多细节。Microsoft/Salesforce 团队把基准提示词改造成类似这种多步往来的形式：

![](/img/sharded_prompt.png)

左侧提示词里的全部信息，都包含在右侧的多条消息中，会在多轮对话里逐步给出。

分片后的提示词带来了显著更差的结果，平均下降 **39%**。团队测试了一系列模型——OpenAI 备受推崇的 o3 得分从 98.1 掉到 64.1。

这是怎么回事？为什么信息分阶段给出，模型就表现得更差？

答案就是*上下文混淆*：拼装起来的上下文包含了完整的对话往来，其中留有模型**在尚未掌握全部信息时**对问题的早期尝试。这些错误答案留在上下文里，并在模型生成最终答案时影响它。论文作者写道：

> 我们发现，LLM 常常在早期轮次中做出假设，并过早尝试生成最终答案，随后又过度依赖这些答案。说得直白些：**当 LLM 在对话中走错方向，它们会迷失，并且回不来。**

这对智能体构建者来说不是好消息。智能体会从文档、工具调用以及负责子问题的其它模型中拼装上下文。所有这些来自不同来源的上下文，都有可能自相矛盾。更进一步，当你连上并非自己创建的 MCP 工具时，它们的描述与指令与你提示词其余部分冲突的概率更大。

百万 Token 上下文窗口的到来曾显得具有变革性。能把智能体可能需要的一切塞进提示词，这激发了对超级智能助手的想象——它们能访问任何文档、连接每一个工具、并保持完美的记忆。

但我们已经看到，更大的上下文制造了新的失效模式。上下文毒化会埋下随时间不断累积的错误。上下文干扰让智能体严重依赖自身上下文、重复过往动作而不向前推进。上下文混淆导致使用不相关的工具或文档。上下文冲突制造内部矛盾，让推理脱轨。

**这些失效对智能体打击最大**，因为智能体恰恰运行在上下文容易膨胀的场景中：从多个来源收集信息、连续进行工具调用、开展多轮推理、并累积大量历史。

所幸，是**有**解决办法的！在接下来的一篇文章中，我们会介绍缓解或规避这些问题的方法，从动态加载工具到建立上下文隔离区。
