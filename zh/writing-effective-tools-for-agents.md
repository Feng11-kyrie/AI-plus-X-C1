[模型上下文协议（MCP）](https://modelcontextprotocol.io/docs/getting-started/intro)能让 LLM 智能体拥有多达数百个工具去解决真实世界的任务。但我们要如何让这些工具**效用最大化**？

本文介绍我们在各类智能体 AI 系统中提升表现的最有效技术¹。

我们先讲如何：

- 构建并测试你的工具原型
- 与智能体一起对你的工具做全面评估
- 与 Claude Code 这类智能体协作，自动提升工具的表现

最后，我们给出在这一过程中总结出的高质量工具编写原则：

- 选择该实现（以及**不该**实现）的工具
- 用命名空间为工具划定清晰的功能边界
- 从工具向智能体返回有意义的上下文
- 为 Token 效率优化工具响应
- 对工具描述与规格说明做提示词工程

*构建评估能让你系统地度量工具的表现。你可以用 Claude Code 针对这套评估自动优化你的工具。*

## 什么是工具？

在计算领域，确定性系统在给定相同输入时每次都会产出相同输出；而**非确定性**系统——比如智能体——即便起始条件相同，也可能生成各不相同的响应。

我们传统上写软件时，是在确定性系统之间建立一份契约。例如 `getWeather("NYC")` 这样的函数调用，每次调用都会以完全相同的方式获取纽约市的天气。

工具是一类新的软件，它体现的是**确定性系统与非确定性智能体之间的契约**。当用户问「我今天该带伞吗？」，智能体可能去调用天气工具，可能凭常识作答，甚至可能先追问一句地点。偶尔，智能体也可能产生幻觉，或者根本没弄明白该怎么用某个工具。

这意味着为智能体写软件时，我们必须从根本上重新思考做法：**不能再用为其他开发者或系统写函数和 API 的方式去写工具和 [MCP 服务器](https://modelcontextprotocol.io/)**，而要为智能体而设计。

我们的目标是扩大智能体能够有效发挥的作用面——让它们借助工具去采取各种成功策略，解决范围广泛的任务。所幸以我们的经验，**对智能体最「顺手」的工具，最终对人类来说也出奇地直观易懂。**

## 如何编写工具

本节介绍如何与智能体协作，既写出工具、也持续改进你交给它们的工具。先快速搭出一个工具原型并在本地测试。接着跑一套全面的评估，用以度量后续改动。与智能体并肩工作，你可以不断重复「评估—改进」这个过程，直到智能体在真实任务上取得良好表现。

### 构建原型

不亲自动手，很难预料哪些工具智能体用起来顺手、哪些不顺手。先快速搭一个原型。如果你用 [Claude Code](https://www.anthropic.com/claude-code) 来写工具（可能一次就成），那么把你工具所依赖的软件库、API 或 SDK（包括可能的 [MCP SDK](https://modelcontextprotocol.io/docs/sdk)）的文档提供给 Claude 会很有帮助。对 LLM 友好的文档通常可以在官方文档站点的扁平 `llms.txt` 文件里找到（这是我们 [API 的](https://docs.anthropic.com/llms.txt)）。

把你的工具包进一个[本地 MCP 服务器](https://modelcontextprotocol.io/docs/develop/connect-local-servers)或[桌面扩展](https://www.anthropic.com/engineering/desktop-extensions)（DXT），就能在 Claude Code 或 Claude Desktop 应用中连接并测试它们。

要把本地 MCP 服务器连接到 Claude Code，运行 `claude mcp add <name> <command> [args...]`。

要把本地 MCP 服务器或 DXT 连接到 Claude Desktop 应用，分别进入 `Settings > Developer` 或 `Settings > Extensions`。

工具也可以直接传入 [Anthropic API](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview) 调用，用于程序化测试。

亲自试用这些工具，找出粗糙之处。从你的用户那里收集反馈，从而建立起对其预期用例与提示词的直觉。

### 运行评估

接下来，你需要通过运行评估来衡量 Claude 使用你工具的表现。先从生成大量植根于真实用途的评估任务开始。我们建议与智能体协作，帮你分析结果并确定如何改进工具。完整流程可参见我们的[工具评估 cookbook](https://platform.claude.com/cookbook/tool-evaluation-tool-evaluation)。

*我们内部 Slack 工具在留出测试集上的表现*

**生成评估任务**

有了早期原型，Claude Code 可以快速探索你的工具，并创建几十组提示词与响应对。提示词应当源自真实用途，并基于真实的数据源与服务（例如内部知识库与微服务）。我们建议避免那种过于简单、流于表面的「沙箱」环境——它们无法用足够的复杂度去压测你的工具。好的评估任务可能需要多次工具调用——甚至几十次。

以下是一些**好的**任务示例：

- 下周与 Jane 安排一次会议，讨论我们最新的 Acme Corp 项目。附上上次项目规划会议的记录，并预订一间会议室。
- 客户 ID 9182 反映，一次购买尝试被扣了三次款。找出所有相关日志条目，并判断是否有其他客户受同一问题影响。
- 客户 Sarah Chen 刚刚提交了取消申请。准备一份挽留方案。要确定：(1) 他们为什么离开，(2) 什么样的挽留方案最有吸引力，(3) 在提出方案之前我们应当注意哪些风险因素。

以下是一些**较弱的**任务示例：

- 下周与 jane@acme.corp 安排一次会议。
- 在支付日志中搜索 purchase_complete 和 customer_id=9182。
- 找出客户 ID 45892 提交的取消申请。

每个评估提示词都应配一个可验证的响应或结果。你的验证器可以简单到把标准答案与采样响应做精确字符串比较，也可以复杂到请 Claude 来评判响应。避免使用过于严苛的验证器——它们会因为格式、标点或合理的替代表述这类无关差异，而否掉正确的响应。

对于每组提示词—响应对，你还可以选择性地指定预期智能体在解决该任务时应调用的工具，以便在评估中衡量智能体是否成功把握了每个工具的用途。不过，由于正确解决任务可能存在多条有效路径，请尽量避免把策略规定得过死或过拟合。

**运行评估**

我们建议用直接调用 LLM API 的方式以程序化方式运行评估。使用简单的智能体循环（用 `while` 循环包裹交替进行的 LLM API 调用与工具调用）：每个评估任务一个循环。每个评估智能体应被给予单个任务提示词与你的工具集。

在评估智能体的系统提示词中，我们建议指示智能体不仅输出结构化响应块（用于验证），还要输出推理与反馈块。指示智能体把这些内容放在工具调用与响应块**之前**输出，可能通过触发思维链（CoT）行为来提升 LLM 的有效智力。

如果你用 Claude 运行评估，可以直接开启[交错思考](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking)来「开箱」获得类似能力。这有助于探查智能体为什么调用或不调用某些工具，并凸显工具描述与规格说明中具体的改进点。

除顶层准确率外，我们建议收集其它指标，例如单次工具调用与任务的总运行时长、工具调用总次数、Token 总消耗量，以及工具错误数。跟踪工具调用有助于揭示智能体常走的共性工作流，也为工具合并提供了一些机会。

**分析结果**

智能体是你发现问题的得力伙伴，它们能就各种事情给出反馈——从自相矛盾的工具描述，到低效的工具实现，再到令人困惑的工具 schema。但要记住：**智能体在反馈与响应中省略的东西，往往比它们写出来的更重要。** LLM 并不总是[言为心声](https://www.anthropic.com/research/tracing-thoughts-language-model)。

留意智能体在哪里卡住或困惑。通读评估智能体的推理与反馈（或 CoT），找出粗糙之处。检查原始记录（包括工具调用与工具响应），捕捉智能体 CoT 中未明确描述的任何行为。要读出字里行间的意思；记住你的评估智能体并不一定知道正确答案与策略。

分析你的工具调用指标。大量冗余的工具调用可能意味着分页或 Token 上限参数需要调到合适大小；针对非法参数的大量工具错误，可能意味着工具需要更清晰的描述或更好的示例。我们发布 Claude 的[网页搜索工具](https://www.anthropic.com/news/web-search)时发现，Claude 会毫无必要地往工具的 `query` 参数后面追加 `2025`，这使搜索结果产生偏置并拉低了表现（我们通过改进工具描述把 Claude 引回了正轨）。

### 与智能体协作

你甚至可以**让智能体替你分析结果并改进工具**。只需把评估智能体的记录拼接起来、粘贴进 Claude Code。Claude 擅长分析记录并一次性重构大量工具——例如，确保在新改动发生时，工具的实现与描述始终保持自洽。

事实上，本文中的大部分建议，都来自我们用 Claude Code 反复优化内部工具实现的过程。我们的评估建立在自己的内部工作区之上，复刻了内部工作流的复杂度，包含真实项目、文档与消息。

我们依靠留出测试集来确保没有对「训练用」评估过拟合。这些测试集显示，我们还能榨出额外的表现提升——甚至超出「专家级」工具实现所能达到的水平，无论那些工具是研究人员手写的，还是 Claude 自己生成的。

下一节我们分享从这个过程中学到的一些东西。

## 编写高效工具的原则

本节把我们的经验提炼成几条编写高效工具的指导原则。

### 为智能体选择合适的工具

**工具越多，未必结果越好。** 我们观察到的一个常见错误，是工具仅仅把现有的软件功能或 API 端点包一层——不管这些工具是否适合智能体。这是因为智能体相对于传统软件有着不同的「可供性」（affordance）——也就是说，它们感知自己能用这些工具采取哪些潜在行动的方式是**不同的**。

LLM 智能体的「上下文」是有限的（即它们一次能处理的信息量有上限），而计算机内存廉价且充裕。设想在通讯录里查找联系人的任务。传统软件程序可以高效地存储并逐条处理联系人列表，检查完一个再处理下一个。

但如果 LLM 智能体用的工具返回**全部**联系人、然后必须逐 Token 通读一遍，那它就在把有限的上下文空间浪费在无关信息上（想象你翻遍通讯录每一页、从上到下找一个人——也就是暴力搜索）。更好、也更自然的方式（对智能体和人类都一样）是先直接跳到相关的那一页（也许是按字母顺序找到它）。

我们建议围绕少数几个高影响的特定工作流，精心打造少量工具，与你的评估任务相匹配，再由此扩展。在通讯录这个例子里，你可以选择实现 `search_contacts` 或 `message_contact` 工具，而不是 `list_contacts`。

工具可以**合并功能**，在底层处理潜在的多项离散操作（或 API 调用）。例如，工具可以用相关元数据充实响应，或在单次工具调用中处理那些经常被链式组合的多步任务。

以下是一些例子：

- 与其实现 list_users、list_events 和 create_event 三个工具，不如考虑实现一个 schedule_event，它会查找可用时间并安排事件。
- 与其实现 read_logs，不如考虑实现 search_logs，它只返回相关日志行与一些周边上下文。
- 与其实现 get_customer_by_id、list_transactions 和 list_notes，不如实现 get_customer_context，一次性汇总某位客户全部近期且相关的信息。

确保你构建的每个工具都有清晰、独特的用途。工具应当让智能体能够像人类在获得同样底层资源时会做的那样去拆分并解决任务，同时减少那些本会被中间输出消耗掉的上下文。

工具太多或功能重叠，也会让智能体分心、不去追求高效策略。对要构建（以及**不**构建）哪些工具做审慎而有取舍的规划，回报很实在。

### 为你的工具加命名空间

你的 AI 智能体可能会接触到几十个 MCP 服务器与数百个不同工具——包括其他开发者提供的。当工具在功能上重叠、或用途含糊时，智能体就会搞不清该用哪个。

**命名空间**（把相关工具归到共同前缀之下）有助于在大量工具之间划出边界；MCP 客户端有时会默认这样做。例如按服务加命名空间（如 `asana_search`、`jira_search`）、按资源加命名空间（如 `asana_projects_search`、`asana_users_search`），都能帮智能体在对的时间选到对的工具。

我们发现，在前缀式与后缀式命名空间之间做选择，对工具使用评估有**不容忽视**的影响。这种影响因 LLM 而异，我们建议你依据自己的评估来选择命名方案。

智能体可能调错工具、用错参数调用对的工具、调用工具过少，或错误地处理工具响应。有选择地实现那些名字能体现任务自然拆分的工具，你就能同时减少载入智能体上下文的工具与工具描述数量，并把智能体侧的运算从上下文卸载回工具调用本身。这会降低智能体犯错的整体风险。

### 从工具返回有意义的上下文

同理，工具实现应当注意只把**高信号**信息返回给智能体。它们应优先考虑上下文相关性而非灵活性，并避开底层技术标识符（例如 `uuid`、`256px_image_url`、`mime_type`）。而 `name`、`image_url`、`file_type` 这类字段，更有可能直接指导智能体的下游动作与响应。

智能体处理自然语言的名称、术语或标识符，也明显比处理晦涩标识符更顺利。我们发现，仅仅把随意的字母数字 UUID 换成语义上更有意义、更可解读的语言（甚至只是一个从 0 开始索引的 ID 方案），就能通过减少幻觉显著提升 Claude 在检索类任务中的精确度。

在某些情况下，智能体可能需要同时与自然语言和技术标识符输出打交道，哪怕只是为了触发下游工具调用（例如 `search_user(name='jane')` → `send_message(id=12345)`）。你可以通过在工具中暴露一个简单的 `response_format` 枚举参数来同时支持两者，让智能体控制工具返回 `"concise"`（简洁）还是 `"detailed"`（详细）响应（见下图）。

你还可以增加更多格式以获得更大灵活性，类似 GraphQL 那样精确选择你想要收到的信息片段。下面是一个控制工具响应详略程度的 ResponseFormat 枚举示例：

```
enum ResponseFormat {
   DETAILED = "detailed",
   CONCISE = "concise"
}
```

### 为 Token 效率优化工具响应

优化上下文质量很重要。但优化工具响应返回给智能体的上下文**数量**同样重要。

对于任何可能消耗大量上下文的工具响应，我们建议实现分页、范围选择、过滤和／或截断的某种组合，并配以合理的默认参数值。对 Claude Code，我们默认把工具响应限制在 25,000 Token。我们预计智能体的有效上下文长度会随时间增长，但对上下文高效工具的需求会一直存在。

如果你选择截断响应，务必用有用的指引来引导智能体。你可以直接鼓励智能体采用更省 Token 的策略，例如在知识检索任务中做多次小范围、有针对性的搜索，而不是一次宽泛的大搜索。同样，如果某次工具调用报错（例如在输入校验时），你可以对自己的错误响应做提示词工程，让它们清楚传达具体、可执行的改进方向，而不是抛出不透明的错误码或堆栈。

### 对工具描述做提示词工程

现在我们来到改进工具最有效的方法之一：**对工具描述与规格说明做提示词工程**。因为它们会被载入智能体的上下文，它们合起来能把智能体引导向有效的工具调用行为。

写工具描述与规格说明时，想一想你会如何向团队里的新同事介绍这个工具。考虑你可能默认带入的上下文——特殊的查询格式、小众术语的定义、底层资源之间的关系——并把它显式写出来。通过清晰描述（并用严格的数据模型强制）预期的输入与输出来避免歧义。特别是，输入参数应当命名得毫无歧义：与其用名为 `user` 的参数，不如试试 `user_id`。

有了评估，你就能更有把握地度量提示词工程带来的影响。即便对工具描述做细微打磨，也可能带来显著的改进。我们对工具描述做了精确优化之后，Claude Sonnet 3.5 在 [SWE-bench Verified](https://www.anthropic.com/engineering/swe-bench-sonnet) 评估上取得了当时的最优表现，错误率大幅下降、任务完成度提升。

工具定义的其它最佳实践见我们的[开发者指南](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#best-practices-for-tool-definitions)。如果你在为 Claude 构建工具，我们还建议读一读工具是如何被动态载入 Claude [系统提示词](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#tool-use-system-prompt)的。最后，如果你在为 MCP 服务器编写工具，[工具注解](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)有助于披露哪些工具需要开放世界访问权限，或会做破坏性改动。

## 展望

要为智能体构建有效的工具，我们需要把软件开发实践从可预测、确定性的模式，重新定向到非确定性的模式上。

通过本文描述的这套迭代式、评估驱动的方法，我们识别出了一些让工具成功的稳定规律：有效的工具被有意而清晰地定义、审慎地使用智能体上下文、能在多样工作流中相互组合，并让智能体以直觉方式解决真实任务。

未来，我们预期智能体与世界交互的具体机制会持续演进——从模型上下文协议（MCP）的更新，到底层 LLM 本身的升级。有了这套系统化、评估驱动的工具改进方法，我们就能确保当智能体变得更强时，它们所用的工具也随之共同演进。
