企业需要超越传统手段的先进安全策略，以应对这些不断增长的威胁。正因如此，企业主需要了解 SAST、DAST 与 RASP 这类安全方案——它们能为应用提供多层防护。

*(延伸阅读：* *[应用安全详解](/en_us/blog/learn/application-security-requirements.html)* *与* *[常见软件测试方法](/en_us/blog/learn/software-testing.html)。)*

## 什么是 SAST？

静态应用安全测试（SAST）是一种[白盒](https://en.wikipedia.org/wiki/White-box_testing)安全测试方法。SAST [利用应用的静态源代码](/en_us/blog/learn/static-code-analysis.html)或二进制文件来识别漏洞。也就是说，SAST 工具在应用**未运行**的状态下对代码进行分析。

开发者用 SAST 检测各类安全风险，例如代码中的[跨站脚本攻击（XSS）](/en_us/blog/learn/cross-site-scripting-xss-attacks.html)、不安全的反序列化、缓冲区溢出，以及[其它 OWASP 漏洞](/en_us/blog/learn/owasp-top-10.html)。由于单靠 SAST 无法识别运行时特有的漏洞，开发者常常必须把 SAST 与其它测试方法结合起来，才能实现全面的安全。

SAST 是[软件开发生命周期](/en_us/blog/learn/software-development-lifecycle-sdlc.html)的重要组成部分，因为它能**尽早**发现漏洞。越早发现，修复成本越低。由于 SAST 工具可以在开发阶段执行，开发者如今能在产品发布上市之前，对代码编写并测试**上千次**（！！）。

SAST 可以集成进 [CI/CD 管线](/en_us/blog/learn/ci-cd-devops-pipeline.html)，这样做时它被称为「安全 DevOps」或「[DevSecOps](/en_us/blog/learn/devsecops-concepts-principles.html)」。SAST 借助自动化具备良好的可扩展性。能够把覆盖 SAST 技术的自动化测试落地，使它成为快速应对代码层风险的高效方案。

## 什么是 DAST？

动态应用安全测试是一种[黑盒](https://en.wikipedia.org/wiki/Black-box_testing)测试方法。DAST 中[「动态」一词](https://en.wikipedia.org/wiki/Dynamic_application_security_testing)意味着，这种方法是在应用**正在运行**时评估其安全性。与 SAST 不同，DAST 不需要访问应用的源代码。它做的是：

1. 模拟外部攻击者的行为。
2. 从外部测试应用，以识别那些仅在运行时才浮现的漏洞。

DAST 能够识别各类安全缺陷，例如拒绝服务（DoS）漏洞与不安全的服务器配置。通过模拟真实世界的攻击场景，DAST 工具评估应用如何响应这些模拟威胁。借助这种方式，开发者能发现 SAST 这类静态测试方法可能漏掉的弱点。

通常，开发者在软件开发生命周期的后期阶段执行 DAST，往往就在部署之前。通过在真实运行环境中测试应用，DAST 提供了对运行时安全的清晰概览，并支撑应用以更好的表现抵御潜在攻击。

## SAST 如何工作？

开发者使用 [SAST 工具](https://en.wikipedia.org/wiki/List_of_tools_for_static_code_analysis)套用预定义规则及其它检测方法——例如模式匹配与数据流分析——来识别编码错误与其它漏洞。他们把这些工具集成进 IDE 或 CI/CD 管线，在编码与测试阶段自动执行扫描。

### 常见的 SAST 方法

以下是 SAST 中常用的一些方法。

![常见的静态应用安全测试方法](/content/dam/splunk-blogs/images/media_14bcb87a7461de3b7ba525cf6cf4c9c17338a9433/common-static-aplication-security-testing-methods.avif?width=750&format=avif&optimize=medium)

**模式匹配**：扫描代码库，寻找已知的不安全编码实践模式。例如使用弱加密算法或不安全的 API 调用。

**数据流分析**：追踪数据如何在应用中流动。通过追踪不可信输入到敏感操作的路径，可以识别 [SQL 注入](/en_us/blog/learn/sql-injection.html)或缓冲区溢出这类漏洞。

**控制流分析**：分析应用的控制结构，例如循环与条件分支，以揭示逻辑缺陷或竞态条件这类潜在漏洞。

**自定义规则创建。** 许多工具允许开发者创建自定义规则来落实编码最佳实践。以下是这类自定义规则的一些例子：

- 标记 SQL 查询中任何使用未净化输入的地方。
- 识别把用户提供的数据输出到浏览器、却未做恰当转义的代码。
- 高亮使用有漏洞或已废弃函数的地方，例如 JavaScript 中的 `eval()` 或 C 中的 `strcpy()`。
- 检测源代码中硬编码的 API 密钥与密码，并标出任何对用户提供数据缺少输入校验的地方。

**依赖扫描。** 一些 SAST 工具会分析应用所使用的第三方库与框架，以识别依赖中的漏洞。

**语义分析。** 通过解读代码的含义而不仅是结构，SAST 工具能检测不安全的配置或 API 误用。

**机器学习模型：** 先进的 SAST 工具引入机器学习算法，通过分析大规模数据集中的模式来识别此前未知的漏洞。

### 使用 SAST 工具时的性能考量

SAST 工具往往需要[大量 CPU](/en_us/blog/learn/cpu-vs-gpu.html) 与内存资源。在分析大型代码库时，这可能成为大问题。对一百万行代码做一次完整扫描，可能消耗数 GB 内存。

SAST 扫描所需时间会随代码库规模剧烈变化——小型项目几分钟，企业级应用则可能数小时。这会影响：

- 构建管线的时长
- 开发者生产力

可以考虑使用支持**增量扫描**的现代 SAST 工具，只分析改动过的代码，而不是整个代码库。

此外，通过规则选择与范围界定来做性能调优至关重要。配置不当的 SAST 工具会不必要地分析非关键代码路径，白白浪费时间与资源，却带不来任何安全收益。

## DAST 如何工作？

DAST 工具模拟真实世界的攻击——例如向输入字段投送各种形式的恶意数据，观察应用如何处理——以识别应用行为与响应中的漏洞与弱点。

### DAST 的步骤

该流程通常包含以下步骤。

![动态应用安全测试步骤](/content/dam/splunk-blogs/images/media_1aece54bbf699307808799045108b90d64c19ee54/dynamic-application-security-testing-steps.avif?width=750&format=avif&optimize=medium)

**第 1 步：扫描。** 扫描 Web 应用以发现入口点（例如 URL、表单与 API）。这一步描绘出应用的结构，并识别[潜在攻击面](/en_us/blog/learn/attack-surfaces.html)。

**第 2 步：攻击模拟。** 通过向应用发送精心构造的请求来模拟恶意活动。这些请求尝试利用各入口点，以测试跨站脚本与跨站请求伪造等漏洞。

**第 3 步：漏洞检测。** 分析应用的响应以识别安全弱点。它评估应用在受攻击时是否表现得符合预期。例如，可以注入恶意数据来检测 SQL 注入缺陷。

**第 4 步：报告。** 生成包含所检测漏洞与修复建议的报告。开发者可以利用报告中的结果来修复已识别的问题。

现代 DAST 方案可以引入 AI 驱动分析、[实时数据集成](/en_us/blog/learn/real-time-data.html)等高级特性。它们会自动创建测试集，动态适应应用结构，并使用机器学习算法把误报降到最低。

### 使用 DAST 工具时的性能考量

使用 DAST 工具时有几处性能瓶颈需要留意。

- DAST 工具会主动与运行中的应用交互，临时推高应用服务器与 Web 服务器的 CPU 与内存占用。
- DAST 扫描期间产生的大量并发请求会消耗可观的网络带宽。
- DAST 扫描器常通过生成唯一请求来绕过或使应用缓存失效，从而降低缓存机制的有效性。
- DAST 工具创建与管理多个测试会话，会提高应用服务器的内存占用。

要避免这些问题、或尽可能降低其影响，请遵循以下做法。

- 把 DAST 扫描安排在应用使用量最低的非高峰时段。
- 在与生产环境一致的预发布（staging）或准生产环境中执行扫描。
- 使用 DAST 工具中的限速功能来控制并发请求数。
- 在扫描期间增大应用服务器的线程池。
- 为 DAST 扫描器的 IP 配置独立的缓存策略。
- 当性能阈值被突破时，实现扫描的自动暂停。

## SAST 与 DAST：关键区别

下表概括了 SAST 与 DAST 的区别。

| 对比维度 | SAST | DAST |
|---|---|---|
| 测试类型 | 白盒测试。在可访问源代码的前提下，从内部向外测试应用。 | 黑盒测试。在无法访问源代码的前提下，从外部测试应用。 |
| 支持的软件类型 | 支持多种软件类型，包括 Web 应用、Web 服务与富客户端。 | 支持 Web 应用与 Web 服务，但通常不支持其它软件类型。 |
| 在 SDLC 中的阶段 | 在软件开发生命周期早期执行。 | 在 SDLC 后期执行，往往在部署期间或之后。 |
| 检测到的漏洞 | 识别编码缺陷，例如：SQL 注入、跨站脚本攻击（XSS）、缓冲区溢出等。 | 检测运行时问题，例如服务器配置错误、拒绝服务漏洞，以及应用层缺陷。 |
| 修复漏洞的成本 | 较低，因为问题在 SDLC 早期就被识别。 | 较高，因为漏洞发现得晚，往往需要紧急修复才能按时部署。 |
| 运行时与环境问题 | 无法检测运行时特有或与环境相关的漏洞。 | 能识别仅在运行时出现、或因环境因素而产生的漏洞。 |
| 深度与广度 | 对代码层漏洞提供深入洞察。 | 对应用的外部安全风险提供宏观视角。 |
| 与工具的集成 | 与 IDE 及 CI/CD 管线集成，实现自动化静态分析。 | 与 CI/CD 管线集成，实现持续的运行时测试。 |
| 误报与漏报 | 由于深度代码分析，误报概率较高。 | 误报较低，但由于内部可见性有限，漏报风险较高。 |
| 技术依赖 | 依赖编程语言与框架，需要与工具兼容。 | 与应用框架无关，因为它们从外部与应用交互。 |

## SAST 与 DAST 的优缺点

### SAST 的优点

- 在软件开发生命周期早期识别安全漏洞。
- 分析代码库，包括基础函数与复杂分支。
- 直接作用于源代码，无需应用运行。
- 提供实时反馈与全面洞察，例如漏洞的确切位置。
- 生成可导出的报告，可用仪表盘跟踪。
- 支持自动化，因此比人工代码评审更快、更高效。

### SAST 的缺点

- 往往产生大量误报，因此可能需要人工复核。
- 无法识别运行时或环境特有的漏洞，例如配置错误。
- 需要针对每种编程语言的专用工具，因此维护复杂。
- 在理解外部库、API 与 REST 端点方面较为吃力。

### DAST 的优点

- 识别仅在应用执行期间才出现的漏洞。
- 从外部操作，无需访问源代码。这对测试第三方应用或已编译代码很有效。
- 模拟真实攻击场景，识别 SAST 漏掉的风险。
- 与应用所使用的编程语言无关。
- 评估整个应用与系统，包括内存消耗、资源使用与第三方接口。

### DAST 的缺点

- 只关注应用的外层，可能漏掉更深层的漏洞。
- 在 SDLC 中应用得较晚，因此修复更昂贵、更耗时。
- 会漏掉某些 SAST 工具通过源代码分析能识别的漏洞。举个例子：某 Web 应用使用不安全的随机数生成器（例如 JavaScript 中的 `Math.random()`）来创建会话令牌。DAST 可能漏掉这个缺陷，因为它只测试运行时行为。（但 SAST 能检测出来。）
- 对大型项目以及需要多实例并行运行的应用，需要定制基础设施，因此资源开销大。

## 什么时候该用 SAST，什么时候该用 DAST？

SAST 与 DAST 在保障 SDLC 安全上扮演互补的角色。理解各自适用的时机，有助于实现全面的安全覆盖。

### 什么时候用 SAST

**在开发早期阶段。** 开发者在 SDLC 早期用 SAST 识别 SQL 注入、硬编码凭据这类漏洞。在部署前抓住这些问题，可以降低修复的成本与复杂度。

例如：SAST 工具扫描 Python 代码，标出一个把硬编码 API 密钥写进源代码的漏洞。开发者重构代码，改用环境变量来安全地存储与读取密钥。

**用于代码评审。** SAST 可集成进版本控制系统，让开发者在提交代码之前先做扫描，从而确保只有安全的代码进入仓库。

示例：SAST 工具能检测出「直接用用户输入拼接文件路径而未做校验」的漏洞——这会让应用暴露于路径遍历攻击。开发者通过净化输入、并使用安全的库函数处理文件路径来修复该问题。

**在持续集成／持续交付管线中。** SAST 在 CI/CD 过程中运行自动化扫描，为开发者提供实时反馈。

### 什么时候用 DAST

**预发布测试。** 开发者在预发布或 QA 环境中用 DAST 识别运行时漏洞（例如不安全的配置、认证缺陷、访问控制不足）。

示例：DAST 工具能检测出暴露敏感数据的数据库配置错误。开发者随后可在部署前把配置修安全。

**在部署后监控中。** DAST 工具持续扫描已部署的应用，寻找由环境变化或新出现的威胁所引发的漏洞。这保证应用随时间推移始终保持安全。

**测试第三方集成。** DAST 能模拟外部攻击者的视角，识别第三方 API 或互连系统中的漏洞。

例如：DAST 工具测试某个 Web 应用时，发现第三方支付 API 中存在漏洞——信用卡信息正通过未加密的 HTTP 连接传输。开发者通过为所有 API 通信强制启用 HTTPS 来解决该问题。

## 哪个更有效：SAST 还是 DAST？

SAST 与 DAST 的有效性取决于：

- 所处的 SDLC 阶段
- 所要应对的漏洞类型

SAST 在开发早期效果最好，主要用于识别源代码中的漏洞、降低成本并推动安全编码实践。相比之下，DAST 关注预发布或已部署应用中的运行时漏洞，能就配置错误、不安全集成等问题提供洞察。

### 采用混合方案

与其二选一，不如**把 SAST 与 DAST 结合起来，形成多层安全策略，同时覆盖静态代码与运行时环境中的漏洞**。SAST 可以集成进开发早期阶段，在应用编译之前发现并修复代码层问题。当应用在测试环境中运行起来后，DAST 则能识别运行时漏洞，并评估应用在攻击条件下的行为。

在 CI/CD 管线中把 SAST 与 DAST 扫描都自动化，能在不牺牲安全的前提下提供持续反馈、加速开发流程。

对于敏捷或 DevOps 环境，加入 IAST 或 RASP 这类工具可以进一步增强安全性。通过把 SAST 与 DAST 的结果相互关联，组织可以实现更全面、更[有效的漏洞管理](/en_us/blog/learn/vulnerability-management.html)。

### 用 RASP 作为 SAST 与 DAST 之外的另一种选择

运行时应用自保护（RASP）是一种高级安全方案，直接安装在应用运行所在的[服务器](/en_us/blog/learn/computer-servers.html)上。

RASP 会把自身嵌入应用的运行时环境。这种集成让 RASP 能分析应用的逻辑与数据。在分析过程中，它可以：

1. 在异常行为发生时即时检测。
2. 立即阻断恶意活动。

一个关键区别是：RASP 不只是对潜在问题发出告警——它通过隔离并处置威胁来主动阻止攻击，而不依赖外部工具。

RASP 为 SAST 与 DAST 提供了一种动态的替代方案。与（分析静态代码的）SAST 和（模拟外部攻击的）DAST 不同，RASP 实时运作。它监控应用执行期间的行为，并通过终止会话或通知防御者来响应实时威胁。

对于绕过网络防御、或在开发阶段被漏掉的漏洞，RASP 的防护尤其有效。

然而，对 RASP 过度自信可能导致组织忽视安全编码实践。此外，由于 RASP 直接运行在应用的运行时环境内，它可能影响应用性能。RASP 无法替代对底层缺陷的修复，但它能在修复进行期间提供持续防护。

正如[一位 RASP 使用者](https://www.gartner.com/peer-community/post/talking-about-app-security-use-rast-tool-substitute-security-control-valuable-add-it-not-valuable-at)所评论的：

「是否采用 RASP 工具，应当基于对应用具体需求与风险画像的充分评估。」

## 未来是 SAST、DAST 与 RASP 并用的 AppSec 测试

应用测试的未来在于把 SAST、DAST 与 RASP 结合起来，构建全面的安全策略。随着安全挑战加剧，把这些工具集成进 CI/CD 管线并自动化其流程将变得不可或缺。

AI 与机器学习的进步会让测试更高效，有助于减少误报并改善威胁检测。

### 金融与金融科技行业

在金融领域，AI 驱动的工具将改变漏洞被检测与缓解的方式。SAST 与 DAST 会继续在开发与预发布阶段识别编码缺陷与运行时问题。

但不会止步于此：RASP 会借助 AI [监控实时交易](/en_us/blog/learn/continuous-monitoring.html)来更进一步。例如，RASP 可以识别异常模式（例如攻击者正试图实时利用某个漏洞），阻断这些活动，同时通知安全团队。

### IoT、边缘与联网设备

在 IoT 领域，这些工具的组合将在保障联网设备安全方面发挥重要作用。具体如下：

- SAST 可以在开发期间确认固件不含漏洞。
- DAST 可以测试设备之间通信协议的安全性。
- 与此同时，RASP 监控已部署的设备，检测并阻止未授权访问尝试，或由新兴威胁导致的数据泄露。

同样，多种方法并用有助于 IoT 生态保持韧性。正如我们在许多示例中所展示的，SAST、DAST 与 RASP 联手，承诺了一个以更强、更主动的安全措施来构建与部署应用的未来。

## 有韧性的安全始于主动测试

把 SAST、DAST 与 RASP 结合起来，可以提供覆盖整个软件开发生命周期的健壮安全。

通过把这些方法集成进 CI/CD 管线，并借助 AI 的进步，组织能够主动应对新兴威胁。这些方法共同构成了一套整体化的路径，让现代应用免于安全漏洞。
