## 摘要

**模型上下文协议（MCP）** 是一项开放标准，它把 AI 模型与外部数据和服务连接起来，让大语言模型（LLM）能够以一致、安全的方式进行结构化的 API 调用。本文将介绍 MCP，解释它为什么对连接 AI 系统有价值，把它与 ChatGPT 插件、手工 API 集成等既有做法作比较，并深入探讨它近期对基于 OAuth 的身份认证的支持。我们还会看一点代码，观察 MCP 的实际运作。

MCP 充当 AI 工具与外部服务之间的**通用适配器**，免去了为每个工具或 API 编写定制集成代码的需要。就像 USB-C 简化了各种设备之间的连接，MCP 为 AI 模型调用外部函数、获取数据或使用预定义提示词提供了统一的方法。它的核心是：**一个接口，连接众多不同系统。**

## 什么是模型上下文协议（MCP）？

MCP 本质上是 AI 应用与外部工具或数据源之间的**通用适配器**。它[定义了一套通用协议](https://www.anthropic.com/news/model-context-protocol#:~:text=MCP%20addresses%20this%20challenge,to%20the%20data%20they%20need)（构建在 JSON-RPC 2.0 之上），让 AI 助手能以结构化方式调用外部服务的函数、获取数据或使用预定义提示词。不必再让每个 LLM 应用为每个 API 或数据库编写定制代码，[MCP 为所有交互提供了一种标准化的「语言」](https://medium.com/data-and-beyond/the-model-context-protocol-mcp-the-ultimate-guide-c40539e2a8e7#:~:text=https%3A%2F%2Fmodelcontextprotocol)。

MCP 这一层让 AI 应用能够安全地访问外部数据源与工具并与之交互。它充任大语言模型（LLM）与各类数据库、应用或 API 之间的桥梁，促成无缝集成与功能实现，而无需大量定制编码。

为实现这一点，MCP 采用**客户端—服务器架构**。由 AI 驱动的应用（例如聊天机器人、IDE 助手或智能体）作为*宿主（host）*，运行一个 MCP *客户端（client）*组件；而每一套外部集成则作为一个 MCP *服务器（server）*运行。服务器通过 MCP 暴露能力（例如函数、数据资源或提示词模板），客户端连接上来以使用这些能力。这种分离意味着 AI 模型**不直接与 API 对话**；而是经由 MCP 的客户端／服务器握手，由这一层来组织数据交换。

[来源](https://generativeai.pub/mcp-servers-explained-python-and-agentic-ai-tool-integration-aa2ddca6cbe5)

## MCP 为什么有价值

在传统做法中，把 AI 模型连到外部数据或动作既繁琐又临时。开发者往往得为想让模型使用的每个 API 或数据库写一次性集成，逐个处理不同的认证方式、数据格式与错误处理。MCP 通过**标准化这些交互**改变了局面。主要收益[包括](https://huggingface.co/blog/Kseniase/mcp#:~:text=,the%20client%20will%20pick%20on)：

- **快速接入工具**：有了 MCP，你可以直接插上新能力，而不必逐个从零写定制代码。如果已有某个 MCP 服务器（比如说，给 Google Drive 或某个 SQL 数据库用的），那么任何兼容 MCP 的 AI 应用都能连上它并立即获得该能力。这对自动化是巨大的胜利——AI 智能体只需加上相应的服务器，就能按需获取文档、查询数据库或调用 API。这就像拥有一个即用型「插件」库，而且它们说同一种语言。MCP 服务器充当轻量程序，通过标准化协议暴露特定能力，充任 Cursor 与各类外部工具或数据源之间的中介。
- **自主智能体**：MCP 让 AI 能表现出更大的自主性。智能体不再局限于内置知识；它们能在多步工作流中主动获取信息或执行动作。例如，一个精密的智能体可以用 MCP 从 CRM 取数据、再通过通讯工具发邮件、再往数据库里记一条日志——全部串成一条无缝的链。通过支持流畅、具备上下文感知的多步交互，MCP 帮助 AI 智能体更接近真正的自主任务执行。正如一位观察者所言，MCP 让 AI 从一个孤立的「大脑」变成多才多艺的「执行者」，因为它获得了对现实世界工具与数据的标准化访问能力。
- **减少摩擦与搭建成本**：由于 MCP 充任通用接口，开发者不必再忍受维护各自独立集成带来的碎片化。一个应用一旦支持 MCP，就能通过同一种机制连接任意数量的服务。每当你想让 AI 使用一个新 API，需要手工搭建的东西都大幅减少。团队可以把精力放在更高层的逻辑上，而不是第十次重新发明连接代码。正如 Anthropic 所说，MCP 用一个更简单、更可靠的单一协议取代了碎片化的集成方案。
- **一致性与互操作性**：MCP 在各类工具之间强制统一的请求／响应格式。这意味着你的 AI 应用不必为 A 服务处理一种 HTTP 响应、为 B 服务处理另一种 XML。模型的输出（函数调用）与工具结果都以统一的 JSON 结构传递。这种一致性让调试与扩展都更容易。它也让你的集成逻辑面向未来——即便你更换底层模型供应商，MCP 与工具之间的接口保持不变。
- **双向上下文**：与简单的 API 调用不同，MCP 支持在模型与工具之间维持上下文与持续对话。除了工具，MCP 服务器还能提供 Prompts（面向特定任务的预定义提示词模板）与 Resources（文档这类数据上下文）。这意味着 AI 不仅能「调用一个 API」，还能摄取参考数据，或在服务器引导下走完复杂工作流。这套协议的设计初衷就是支持丰富交互，而不只是一次性查询。这在编码助手这类应用（AI 可能通过 MCP 与开发环境反复迭代）或需要与多个数据源来回交互的复杂决策任务中尤其有用。

简而言之，MCP 为增强 LLM 带来了**可扩展、即插即用的路径**。它让 AI 系统能安全地接入所需的「实时」数据与动作，而每个开发者不必各自重新发明轮子。MCP 的早期采用者已经为 Google Drive、Slack、GitHub、数据库等工具建好了服务器——展示了 AI 智能体如何借助 MCP 与企业内容仓库、DevOps 工具以及其它现实世界系统打交道。

## MCP 架构——一眼看懂它如何工作

### 客户端—服务器结构

MCP 遵循清晰的客户端—服务器架构：

- **MCP 客户端**：嵌入在 AI 应用中（聊天机器人、IDE 助手、自动化智能体）。
- **MCP 服务器**：暴露外部能力，例如函数（工具）、资源（数据）与提示词（模板）。

所有交互都通过标准化的 JSON-RPC 消息发生，维持一种安全、结构化的数据交换：

**JSON-RPC 请求示例：**

例如，要列出可用的工具，MCP 客户端会发出这样的请求：

```
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}
```

服务器会以结构化 JSON 回复，列出各工具（每个都带名称、描述与输入 schema）。例如，某个服务器可能声明一个 get_weather 工具，并描述它需要哪些输入。

```
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": [
    { "name": "get_weather", "description": "Retrieves weather data.", "schema": { "location": "string" } }
  ]
}
```

之后，当 LLM 决定使用某个工具时，客户端就发起调用。MCP 服务器执行该函数，并以结构化 JSON 响应返回结果。宿主应用内的 MCP 客户端随后可以把该结果回填进模型的上下文或响应。实践中，由宿主应用来中介这个过程：它把 LLM 的意图（通常来自模型的函数调用输出）转成 MCP 请求，再把服务器的结构化结果交回 LLM。这种双向交换是**安全且受控的**——模型只能调用服务器所暴露的那些特定工具，所有进出数据都经由既定的协议。

## 构建与部署 MCP 服务器

构建与部署 MCP 服务器，是把模型上下文协议（MCP）用于 AI 集成的关键一步。MCP 服务器充任 AI 模型与外部数据源或工具之间的中介，促成无缝通信与数据交换。MCP 最突出的特性之一是它在服务器开发上的灵活性。开发者可以使用任何能向 stdout 输出或提供 HTTP 端点的编程语言，从而选择自己偏好的语言与技术栈。

构建 MCP 服务器时，必须考虑架构与设计。MCP 遵循客户端—服务器架构，其中一个宿主应用可以连接多个服务器。这种架构带来了可扩展性与灵活性，让开发者能够设计出处理各类任务与职能的 MCP 服务器，例如数据处理、工具集成或 AI 模型管理。

MCP 服务器可以部署在多种环境中，包括本地开发环境、云平台或本地机房基础设施。例如，Cloudflare 提供了一个健壮的平台来构建与部署远程 MCP 服务器，让 MCP 部署的管理与扩展更容易。这种灵活性确保 MCP 服务器可以针对不同应用与环境的特定需求做定制——无论是供开发用的本地部署，还是用于生产的云端方案。

通过聚焦良好设计的架构并利用 MCP 的灵活性，开发者可以构建强大且可扩展的 MCP 服务器，增强 AI 模型的能力，使其能与外部数据源和工具无缝交互。

## MCP 客户端与工具

MCP 客户端与工具是模型上下文协议生态中不可或缺的组成部分。MCP 客户端是连接 MCP 服务器、以访问外部数据源或工具的应用。这些客户端可以用各种编程语言与框架构建，例如 Python、JavaScript 或 Java，让开发者能灵活地为自身需求选择最合适的工具。

而 MCP 工具则是为 MCP 客户端提供特定能力或功能的软件组件。这些工具可以与 MCP 服务器集成，以实现数据处理、AI 模型管理或工具集成等特性。MCP 工具的例子包括 Claude Desktop（提供与 AI 模型交互的聊天界面）与 Cursor（提供用于扩展 AI 能力的插件系统）。

开发者可以构建自定义的 MCP 客户端与工具，以满足特定用例或需求。这种灵活性让 MCP 生态得以创新与试验，使开发者能创造出新颖有趣的应用。无论是用于数据分析的专用工具，还是能集成多个 MCP 服务器的客户端应用，可能性都非常广阔。

借助 MCP 客户端与工具，开发者可以构建健壮而多才的应用，充分释放 AI 模型的潜力，让它们能与广泛的外部数据源和工具无缝交互。

我们来比较几种在 MCP 之前、或与 MCP 同时存在的做法：

- **自定义集成与 API 密钥管理**：最常见的传统做法是为每个服务写定制代码，并把凭据（API 密钥或令牌）交给 LLM 去使用这些集成。例如，你可能会写一个查询 API 的 Python 函数，把调用该函数的能力给 LLM，并在后端手工管理 API 密钥。这种做法费人力且不可扩展——每新增一个数据源就要写新代码，而每个环境都必须安全地管理 API 密钥。它常常导致系统脆弱，因为每套集成都是独一无二的。相比之下，MCP 把这些交互集中并标准化：AI 智能体只需处理 MCP 这一层，而任何 MCP 服务器（对应任何服务）都能以即插即用的方式工作。新增服务器**完全不需要改动客户端代码**。此外，MCP 为身份认证提供了正式结构（后文讨论），因此把 API 密钥交给 AI 不再是临时起意，而是通过一套安全协议来完成。
- **ChatGPT 插件（OpenAI 插件）**：2023 年，OpenAI 为 ChatGPT 引入了插件系统，让模型能调用由 OpenAPI 规格定义的对外 API。这是走向标准化工具调用的一小步，但它有局限。每个插件本质上都是它自己的小型集成（有自己的 API schema 与认证方式），而且必须逐个构建／托管。只有某些平台（如 ChatGPT 或 Bing Chat）能使用这些插件，因为那是专有方案。插件大多也是一次性调用——模型调用一个 API 拿到信息，没有持久连接或持续交换。MCP 的不同在于它是**开放且通用**的（不绑定于某一个供应商或界面），并支持丰富的双向交互与持续的上下文。可以把 ChatGPT 插件想象成封闭工具箱里的专用工具，而 MCP 是任何开发者或 AI 平台都能使用的开放标准工具包。MCP 标准化的认证（尤其是 OAuth）也意味着，相比 ChatGPT 系统中逐个插件各走一套 OAuth 流程，它能以更统一的方式处理对用户数据的安全访问。总之，ChatGPT 插件展现了为 LLM 标准化 API 访问的价值，而 MCP 更进一步：把它变成开放协议，并在 AI 与服务之间建立起持久的「对话」。
- **LLM 工具框架（LangChain、各类智能体库）**：在 MCP 之前，许多开发者用 LangChain 这类框架给模型配工具。在这些方案里，你定义一组工具函数（带描述）以及智能体的提示词逻辑，让 LLM 决定是否使用它们。这能行得通，但每个工具的幕后仍需要定制实现——LangChain 最终在其库里维护了数百个工具集成。本质上，LangChain 提供的是**面向开发者**的标准（一个 Python 类接口），用于把工具集成进智能体的代码库，但没有为模型提供在运行时动态发现新工具的能力。MCP 与这些框架是互补的，它把标准化转向**面向模型**。有了 MCP，智能体可以发现并使用任何 MCP 服务器提供的工具，即便智能体的代码事先并未显式包含该工具。事实上，LangChain 已加入支持，可以把 MCP 服务器当作又一种工具来源——这意味着用 LangChain 构建的智能体能轻松调用 MCP 工具，从而利用不断壮大的 MCP 服务器生态。区别在于，MCP 把接口通过一套协议（JSON-RPC，带元数据等）正式化，使其更容易接入不同环境，而不只是 Python 框架。类似地，OpenAI 原生的函数调用功能可以看作处理函数调用的**格式**（模型输出一个 JSON 函数调用），而 MCP 以标准化方式处理该调用的**执行**。OpenAI 的函数调用与 MCP 常常协同工作：LLM 产出结构化调用，MCP 客户端／服务器执行它并返回结果，二者合力实现无缝的工具调用。

本质上，MCP 并非第一次尝试把 LLM 与外部 API 连接起来——但它从过去那些做法（插件、工具库等）中吸取经验，并统一了解决方案。它提供一套**开放、与模型无关的协议**，简化了集成与认证。尤其在安全与认证方面，MCP 的设计（支持 OAuth）避免了「逐插件配密钥」的拼凑做法，也避免了把原始 API 密钥交给模型。相反，身份认证可以作为协议的一部分，以一致、标准化的流程来处理——相比现状是重大进步。

## MCP 实战：技术深潜

我们一步步走一遍典型的 MCP 交互，把它的运作方式夯实，并看一点代码。设想我们有一个 AI 助手，想使用某个提供一组工具的 MCP 服务器（假设是给一个叫「Neon」的数据库服务用的）。高层流程是：

**1. 连接 MCP 服务器** —— 宿主应用（AI 助手）初始化一个 MCP 客户端，并与服务器建立连接。取决于服务器位置，这可能通过本地进程（stdio）或远程 HTTP 流（SSE）进行。底层上，客户端会发送一条 initialize 消息，[用于握手协议版本与能力](https://nshipster.com/model-context-protocol/#:~:text=Like%20LSP%2C%20MCP%20has%20clients,The%20server%20responds%20in%20kind)。

**2. 发现可用的工具／资源** —— 客户端随后查询服务器提供什么。如前所示，它可能发送 `{"method": "tools/list"}`，并收到一份工具定义列表。助手可以据此告知 LLM（例如把工具列表放进系统提示词，或通过模型的函数 schema，取决于具体实现）。举例来说，用 SDK 的话，这可能就是一行代码：

```javascript
const tools = await mcpClient.request({ method: 'tools/list' }, ListToolsResultSchema);
```

它返回一个结构化的工具列表。每个工具条目都有名称、描述与输入的 JSON schema，[这样 AI 就知道自己能做什么](https://neon.tech/blog/building-a-cli-client-for-model-context-protocol-servers#:~:text=,can%20use%20during%20our%20interaction)。

**3. LLM 选择工具** —— 当用户向 AI 提出需要外部动作的问题时，LLM 会判断（通常通过提示词工程或函数调用能力）应当使用某个工具。例如用户问：*「AAPL 股票的最新价格是多少？」* LLM 看出应当调用 `get_current_stock_price(company="AAPL", format="USD")`。宿主应用捕获这个意图（例如 OpenAI 的函数调用 API 会以 JSON 返回函数名与参数）。

**4. 通过 MCP 调用工具** —— 客户端随即向服务器发送 `tools/call` 请求，带上选定的工具名与参数。我们前面见过这样的 JSON 示例。在代码里，用 SDK 大概是这样：

```javascript
const result = await mcpClient.request({
    method: 'tools/call',
    params: { name: toolName, arguments: toolArgs }
}, CallToolResultSchema);
```

这会让服务器在其一侧执行该工具的处理函数。服务器可能在调用外部 API、执行数据库查询，或执行该工具封装的任何逻辑。结果（可能是简单值，也可能是复杂的 JSON 对象）会通过 MCP 响应的 result 字段发回。

**5. 把结果交回 LLM** —— MCP 客户端收到工具的输出。现在宿主应用可以把它整合进 AI 的响应。在许多智能体方案中，模式是把结果注入对话并请模型继续。例如，助手可能接着呈现：「AAPL 当前股价为 173.22 美元。」如果使用自动循环，结果可以交给模型（也许以系统消息的形式追加到对话里，例如「get_current_stock_price 的结果：……」），模型便能带着这条信息继续回答用户的提问。

下面是一个简化示意，展示如何使用 Anthropic 的 Claude（原生支持工具调用）在对话中调用工具并使用结果：

```javascript
// 1. Send user prompt to LLM with available tools context
const response = await anthropicClient.complete({
  prompt: "User: Can you list my projects?\nAssistant: ",
  model: "claude-3.5",
  tools: tools // list of tools from MCP server
});
for (const msg of response.messages) {
  if (msg.type === 'tool_use') {
    // 2. LLM decided to use a tool
    const { name, args } = msg;
    // 3. Call the tool via MCP
    const toolRes = await mcpClient.request({ method: 'tools/call', params: { name, arguments: args } });
    // 4. Inject tool result and resume LLM
    await anthropicClient.send({ role: 'system', content: `Tool result: ${toolRes.result}` });
  } else {
    // 5. Handle normal LLM reply (tool result likely integrated)
    console.log("Assistant:", msg.content);
  }
}
```

现实中，框架会替你处理其中大量工作，但上面的伪代码勾勒出 MCP 如何嵌入这个循环。关键在于：**MCP 为工具执行提供了标准化的调用／响应层**，AI 智能体代码可以挂接进去。无论你用的是 OpenAI、Anthropic 还是别的 LLM，MCP 都保持不变——它是模型意图与外部动作之间的黏合剂。

使用 MCP，开发者得到一条清晰、结构化的管线来扩展 AI 能力。代码变得更好维护（因为各处调用的是通用的 `mcpClient.request`，而不是按服务分别写代码），AI 也变得更强（因为它能接入任何支持 MCP 的服务）。调试同样更容易——你可以监控 JSON-RPC 消息，准确看到请求了什么、返回了什么，而不必去解析模型生成的文本来猜线索。

## 早期局限（没有内置身份认证）

MCP 刚出现时（2024 年底），它提供了工具与数据交换的核心协议，但缺少用于连接远程服务器的标准化认证机制。实践中，早期的 MCP 演示与实现往往要求把 MCP 服务器跑在**本地**或受信任的环境中，那里认证不是什么大问题（因为 AI 与服务器跑在同一台机器上）。例如，开发者可以在自己的 [localhost](http://localhost) 上跑一个 Google Drive 的 MCP 服务器，配上一个事先获取的令牌，然后让 AI 应用指向它。但要在互联网上、或与第三方服务一起使用 MCP，没有正式的认证流程就很棘手。

许多早期 MCP 服务器假定用户会在启动时手动把凭据或 API 密钥提供给服务器。举例来说，Anthropic 的快速上手指南建议通过配置或命令行提供你自己的凭据（API 密钥、令牌）来运行预置服务器。这意味着服务器本身能接触到你的密钥，而 MCP 客户端只是信任那个服务器。这对个人或单用户场景可行，但对多用户应用或云端托管的智能体就不太可扩展了。当时没有一套**标准握手**能让 AI 智能体表明：「嘿，我被授权代表用户 X 访问这个服务；这是我的凭据。」

本质上，早期 MCP 客户端除了带外方式（例如预先共享一个令牌，或在无认证状态下运行），没有办法向 MCP 服务器做身份认证。这是一个显著的局限——**MCP 的设计初衷是开放、基于互联网的，但没有认证标准，安全的远程使用就被束缚住了**。

缺少认证标准意味着 **MCP 客户端无法安全地自行连接任意服务器**。你要么把客户端 ID／API 密钥硬编码进客户端（在分布式应用中并不理想），要么只能在没有认证的情况下运行，并假定只有已授权用户能触及该服务器（通常靠把它保持在本地）。显然，要让 MCP 发挥全部潜力（例如以安全方式把 AI 智能体连到云端托管的数据源），需要更好的方案。好消息是社区认识到了这一点，并着手把基于 OAuth 的身份认证内建进 MCP。

### **OAuth 2.0 身份认证流程**

为解决早期的认证局限、增强安全连接能力，MCP 采用了 OAuth 2.0——一个被广泛认可且健壮的身份认证标准。OAuth 2.0 提供了安全、可扩展的框架，让 MCP 客户端能安全地与远程服务器、云端托管资源以及多用户环境交互。把 OAuth 2.0 集成进 MCP 的关键组成与收益包括：

1. **动态客户端注册（DCR）**：模型上下文协议支持动态客户端注册，允许客户端自动向 OAuth 服务器注册。这免去了手工配置客户端或硬编码凭据的需要，显著简化了开发者的部署工作。
2. **自动端点发现**：MCP 利用标准化元数据 URL（遵循 OAuth 的发现协议），让客户端能自动发现 OAuth 端点。这减少了配置开销，让 MCP 部署更容易、更灵活。
3. **安全的授权与令牌管理**：客户端获得精确贴合用户权限与访问范围的 OAuth 令牌。这确保客户端只访问用户明确许可的资源，提升安全性与合规性，在多用户与云环境中尤其重要。
4. **可扩展且安全的多用户支持**：OAuth 2.0 的设计天然支持多个并发用户与服务，解决了 MCP 早期的一大显著局限。应用现在能无缝地为众多用户同时处理授权流程，这对云端的广泛采用至关重要。

## 调试与排障

调试与排障是使用 MCP 服务器和客户端时至关重要的环节。MCP 提供了多种调试与排障的工具与技术，确保开发者能高效地定位并解决问题。其中一个关键工具是 MCP Inspector——一个用于 MCP 服务器的交互式调试工具。

MCP Inspector 让开发者能够测试并检查 MCP 服务器，定位并解决 MCP 服务器集成中的问题。该工具提供 MCP 客户端与服务器之间交互的详细视图，让问题定位与根因理解都更容易。此外，MCP 还提供了一份全面的调试指南，列出常见问题与解决方案，帮助开发者快速排障、解决问题。

调试 MCP 服务器时，必须考虑系统的架构与设计。开发者应当定位造成问题的具体组件或模块，并使用 MCP Inspector 这类工具来诊断与解决。通过坚持系统化的调试方法、并善用现有工具，开发者可以确保自己的 MCP 集成健壮可靠。

## MCP 的真实世界应用

模型上下文协议（MCP）在多个行业与领域都有真实世界的应用。MCP 的主要用例之一是 AI 集成——MCP 在其中促成 AI 模型与外部数据源或工具之间的无缝通信与数据交换。

MCP 可用于各类应用，例如：

- **构建 AI 驱动的聊天机器人**：这类聊天机器人可以访问外部数据源或工具，为用户提供准确、最新的信息。
- **创建 AI 驱动的工作流**：MCP 让 AI 模型能与外部系统或数据源集成，自动化复杂工作流并提升效率。
- **开发 AI 模型**：这些模型能与外部工具或数据源交互，增强自身能力并给出更准确、更相关的输出。
- **实现 AI 驱动的自动化**：在金融、医疗、制造等行业，MCP 能自动化任务与流程，提升生产率并减少错误。

MCP 的灵活性与适应性，使它成为希望在其应用中利用 AI 与机器学习的开发者与组织的诱人方案。通过为 AI 模型与数据源、工具的交互提供标准化接口，MCP 促成了 AI 生态中的创新与试验。这种标准化路径不仅简化了集成过程，也确保 AI 模型能获得发挥最佳表现所需的数据与工具。

总之，MCP 为 AI 应用打开了一片可能性。它让开发者能创造更集成、更自主、更可扩展的方案。无论是用 AI 驱动的聊天机器人提升客户服务，还是自动化工业场景中的复杂工作流，MCP 都提供了把这些创新落地所需的工具与框架。
