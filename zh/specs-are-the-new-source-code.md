在我的职业生涯里，规格说明越写越短。我刚进 Microsoft 时，衡量一个 PM 价值的标准是其所写规格的分量。多年后到了 Tripadvisor，我们把那位拿着餐巾纸上涂的规格来参加产品评审的 PM 传成了传奇。

产品团队常把规格文档当作纸面工作——是在「真正的活」（发布）之前不得不忍受的恶。工程师因优雅的代码受赞誉，设计师因漂亮的体验受赞誉，PM 因交付业务影响受赞誉。但规格文档呢？通常是被匆匆赶完、随手丢在一边、然后被遗忘。

这一直是个错误。在我的[产品能力工具箱](https://www.ravi-mehta.com/product-manager-skills/)里，「功能规格说明」排在十二项能力之首，这是有原因的。它与「产品交付」「产品质量」一起，共同支撑着「产品执行」。

无懈可击的执行是优秀产品管理的根基，而一份出色的规格文档就是起跑线。

今天，我们构建产品的方式正在转变。工程师变得更快——快得多。AI 能在几分钟内把粗糙的想法变成可运行的代码。瓶颈不再是构建，而是**知道该构建什么，并让团队围绕这些需求对齐。**

忽然之间，那份不起眼的规格文档不再是转瞬即逝的纸面工作。它是产品管理的根基——它正在变成源代码本身。

## 为什么 PM 忽然成了瓶颈

在近期题为 [用 AI 更快地构建](https://www.youtube.com/watch?v=RNJCfif1dPY) 的演讲中，Andrew Ng 指出了前所未有的趋势：

> 「我人生中第一次见到有人向我提议，让 PM 的数量达到工程师的两倍。我至今不确定这个提议是不是好主意，但我认为它预示着世界正走向何处。」——Andrew Ng

这印证了我们在[上一篇文章](https://blog.ravi-mehta.com/p/will-ai-kill-product-management)中的预测：随着工程师借助 AI 把交付速度提高数倍，公司**需要更多 PM 去支撑这些高效工程师，而不是更少**。

随着产品交付加速，产品管理其它各个环节都承受着巨大压力——理解客户需求、打磨正确的功能、验证影响。

而所有这些压力，最终都会汇聚到一份产出物上——规格文档。

## 规格——新的源代码

在传统软件开发中，程序员编写人类可读的「源代码」，再被编译成高度优化、机器可读的「目标代码」。「目标代码」（也叫二进制）是可由源代码重新生成的副产品。源代码**字面意义上**就是事实的来源。

来自 OpenAI 的 Sean Grove 提出了一个颇具冲击力的论断。在近期演讲[《新的代码》](https://www.youtube.com/watch?v=8rABwKRsec4)中，他主张：一份写得好的提示词（也就是规格说明）就是新的源代码。

从这个角度看，我们做 AI 开发的方式其实是反的。我们精心雕琢提示词，把自己的意图传达给模型。AI 生成代码。然后我们留下代码，把提示词丢掉。

「这感觉就像你把源代码碎掉，然后非常小心地对二进制做版本控制，」Grove 评论道。

想想看。在传统编程里，源代码是神圣的。源码包含注释、结构和文档——理解并修改这个系统所需的一切。二进制只是个下游产物。

但在 AI 时代，我们把这种关系颠倒了过来。我们把生成的代码当作值得保留的产物，而把规格说明——也就是提示词——当作一次性的东西。

Grove 认为这完全弄反了。代码，即便是优雅的代码，也只是他所说的规格说明的「有损投影」。正如反编译二进制拿不回原有的注释和变量名，读代码也读不出它背后的完整意图。

而规格说明包含一切。一份足够健壮的规格可以生成「好的 TypeScript、好的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客」。

> 「一份足够健壮的规格可以生成好的 TypeScript、好的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客。」——Sean Grove，OpenAI

更重要的是，规格说明能做代码做不到的事：它让**人和机器**在共同目标上对齐。Grove 说得很直白：「一份写下来的规格说明能有效地让人对齐，它是你用来沟通、讨论、辩论、查阅并达成同步的产物。」

他预测：「在不久的将来，沟通最有效的人就是最有价值的程序员。而实际上，只要你能有效沟通，你就能编程。」

新的稀缺技能不是写代码，而是写出能完整承载意图与价值的规格说明。

对产品经理而言，这听起来应该很熟悉。这正是我们一直在做的事——只不过现在，机器也在听。

## 等等，原型不是已经把规格文档干掉了吗？

直到最近，产品生命周期都不得不从规格文档（或 PRD、概念文档、餐巾纸）开始，由它来启动最初的线框图、设计、原型与最小可行产品（MVP）开发。

传统做法让人觉得是不得不忍受的恶。工程师构建基础的 MVP，只为把某样东西——任何东西——送到客户手里。「如果你对产品的第一版不感到难堪，说明你发布得太晚了」成了信条。

我们构建产品的整套方法近来发生了重大转变，在这个新世界里，**规格文档往往是产出，而不是输入**。

今天，你不需要发布一行代码就能把原型送到客户手里。v0、Lovable、Replit 这类工具让你在几小时内——而不是几周内——搭出能跑的原型，而且不需要工程投入。

这不只是更快——而是根本不同。手里有了一个「氛围编程」出来的原型，你可以在写下一行功能规格之前就收集真实客户反馈。你可以验证假设、迭代流程、打磨交互。

- **旧的工作流是这样的**：模糊的想法 → 线框图 → 设计 → 由工程师构建的 MVP → 客户反馈 → 痛苦的规格修订 → 线框图 → 设计 → 重做 → 祈祷。
- **新的工作流**：模糊的想法 → 快速原型 → 客户反馈 → 清晰到不能再清晰的规格 → AI 辅助实现。

原型没有把规格文档干掉。它们让规格文档变得更好。

Danny 将带我们走一遍他们的规格驱动开发流程——这套流程带来了两方面影响：

1. 在较大功能上，与工程团队的沟通效率大幅提升；
2. 让 Danny 尽管此前毫无编码经验，也能在较小的需求上，从详尽的规格一路走到上线的功能。

下面是我最近做的一个例子。作为背景：我们在构建一款产品，让专家型意见领袖能把其网络中的人选推荐到岗位上。上线新的落地页之后，我们需要给专家一个快捷入口，访问他们自己页面的链接。

> *我们需要在页头加一个按钮，跳转到 company-apply 页面。我眼下在忙邮件的事。这个应该可以氛围编程搞定，你要是能接一下就接。*

这来自我的联合创始人，指的是一个需要上线的简单按钮。够简单，而且正是那种如今非技术人员也能自己上线的活。

下面是把这件事在几分钟内做完的配置与步骤：

- **项目管理工具**：[Linear](https://linear.app/homepage)
- **IDE**：[VS Code](https://code.visualstudio.com/)
- **扩展**：[GitHub Copilot Pro](https://code.visualstudio.com/docs/copilot/overview)
- **模型**：[Claude Sonnet 4](https://claude.ai/login?returnTo=/?)
- **MCP 服务器**：[Linear MCP 服务器](https://linear.app/changelog/2025-05-01-mcp)，让 Copilot 能访问 Linear 工单

我们来看这个流程的各个步骤（可对照上面的 Loom 视频）：

1. 从联合创始人的 Slack 消息生成一个 Linear 工单（00:14）
2. 在上面的工单中明确我想要的新文案是什么（00:25）
3. 打开 Copilot，提示 Claude 打开该 Linear 工单（01:18）
4. 提示 Claude 审阅该工单，并结合代码库分析它（01:52）
5. 提示 Claude 创建分支并实现这些改动（02:30）
6. 测试这些改动，确认符合预期（02:52）
7. 在 GitHub 上打开拉取请求（PR），把这些改动合入代码库（03:55）
8. 等待工程师评审／批准该 PR

把镜头拉远，这套配置真正的威力就显现出来了。是的，这是个微不足道的例子，但道理依然成立：一个非技术人员如今可以在 Linear 工单、代码库和工程师之间穿梭，而这一切只靠通过 GitHub Copilot 给 Claude 的几句提示词。

再说一次，这整件事的关键不是代码本身——而是规格。

不过，必须先说明要让这一切顺利运转所需的几个条件：

1. **要具体**：使用含糊的规格只会产出一团乱的代码库。用 Claude 把工单的初稿拿来，结合代码库审阅，并帮它变得更具体——这是流程中不可或缺的一环。在我们这里，我们还写了「好规格该怎么写」的准则。
2. **要有选择性**：把上面这套用在较简单的任务上最理想。工单越复杂，就越需要真正懂行的人参与（在这些情况下，「自助」往往名不副实）。
3. **要有把关**：这套做法之所以行之有效，是因为确实有一位懂行的工程师在评审改动，确保简洁性与功能性之间的平衡得以维持。

但要说清楚：规则已经变了。规格是所有构建产品的人——包括 LLM——的事实来源。

配置得当的话，作为一个非技术人员向代码库贡献代码，完全是现实的期望。只要有足够的时间和耐心，你就能开始理解代码库并自己实现改动，而不是每次都得靠 Claude 来救场。

有一天，你甚至可能期待 AI 智能体在你喝着咖啡时就把工单做完了。

如果你是 PM，正在担心 AI 会怎样影响你的工作，关键在于认识到：**这份工作本身正在改变**。但对其他所有人来说也是如此。好消息是，成为一名优秀 PM 所需的核心能力，在这个新世界里反而更有价值了。

正如我们在[上一篇文章](https://hiringhumans.decimals.work/p/will-ai-kill-product-management-i)中预测的，以这种方式运作的公司会需要更多 PM，而不是更少。而事实证明，这个预测应验得相当不错：

## 规格万岁！

William Gibson 是创造了「赛博空间」一词的科幻作家，他曾说：

> 未来已经到来——只是分布得还很不均匀。

当我想 AI 能做什么、不能做什么时，就会想起这句话。今天，AI 带来的进步极不均衡。有些事情——生成代码、文本、图像——实现了量子式跃迁，它们以 **AI 速度**运转。另一些事情——与客户交谈、发现他们的需求、说服他们购买——仍然以**人类速度**运转。

这种不均衡的分布正在重塑产品团队。聚光灯正从「实现类工作」转向「理解类工作」。那些一直让最优秀的 PM 脱颖而出的核心能力——理解用户需求、清晰地定义问题、设计优雅的方案——其价值呈指数级上升。

最优秀的 PM 会把这些洞察转化为规格——这种规格让团队对齐、指导实现，并成为日益自动化的开发世界中留存下来的产物。
