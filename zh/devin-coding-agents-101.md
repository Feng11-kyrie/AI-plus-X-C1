# 编码智能体 101：把事情真正做成的艺术

时间是 2025 年。**编码智能体不是魔法，但它们大概是我们手上最接近魔法的东西。**我们注意到，有些工程师——尤其是资深到主管级别的那批——比别人更快地取得了成效。这里我们分享一些来自客户与我们自身经验的要点。

关于本指南：

## 与产品无关

我们讨论的技巧能帮你用好**任何**编码智能体。

## 偏实操

我们给出自己最喜欢的、可立即执行的建议。

## 面向技术人

虽然编码智能体对许多人都可能有价值，但本指南是**以工程师为读者**写的。

开发者工具一直在快速演进。十年前，是自动补全与智能提示，能建议方法名并做程序化重构。四年前，是 Copilot 与 Tab 补全，能替你写下接下来几行代码。两年前，是生成式对话机器人，能辅助开发并为你生成整个文件。今天，是自主智能体，能在极少人工干预下，把最初的描述一路做到最终的拉取请求。过去两年，我们通过构建 Devin 专注于把这一愿景变为现实。如今，对自主智能体的关注正达到新高，尤其是近期类似产品的发布之后 [1] 除 Devin 之外，近期发布的产品还包括 OpenAI 的 Codex 与 Google 的 Jules。Cursor、Claude Code 这类本地智能体也可以放在并行工作区里运行，以取得类似效果。。这些智能体可以出现在多种形态中，包括 Web 应用、移动应用，以及集成进 Slack、GitHub、Linear、Jira 等常用工具。

虽然人与 AI 助手结对能比任何单独的 AI 做得更多，但自主智能体**端到端处理任务**的能力带来了新的多任务层级——它把每一位工程师都变成了工程管理者。

适应与这些新 AI 同事高效协作需要一些时间。有意思的是，我们观察到资深到主管级别的工程师往往最快接纳并熟练掌握这些工具。最终，这些工具会在所有级别的工程工作中变得普遍。基于我们的经验与客户反馈，我们想分享关键洞察与经验教训，帮每个人成功地把这些工具融入自己的工作流。

## 提示词基础

这些基本准则能帮你在 2025 年有效地与编码智能体交互。哪怕别的都没记住，至少也要记住这几条。

### 不仅说**做什么**，还要说**怎么做**

把智能体想象成一位判断力不太可靠的初级编码伙伴。简单任务可以直接描述，但对更复杂的任务，一开始就清楚说明你偏好的做法。提前把整体架构与逻辑给到智能体，不仅提高它成功的概率，也减少你评审代码的时间——因为你已经熟悉了预期的方法。

#### 示例：

不要说「加单元测试」，而要指明要测什么功能、指出重要的边界情况，并说清哪些东西需要 mock（如果需要的话）。

### 告诉智能体从哪里开始

想一想如果你自己做这个任务，会从哪里入手。即便你不知道具体的文件或函数名，也要提到相关仓库、相关文档以及涉及的关键组件。明确点出这些要素，能最大限度减少无用功与困惑。

#### 示例：

「请给我们的代码加上对 Google 模型的支持。你应该看一下[这里](link)的最新文档，并在模型组目录下新建一个实现文件。」

### 练习防御性提示

想象你把同样的提示词交给一位新来的实习生。哪里最可能出现困惑或错误？预判这些点，主动把你的说明讲清楚，避免歧义。

#### 示例：

「请修复我们搜索模块的 C++ 绑定，让它通过新的单元测试。注意，你很可能每次改动代码后都要重新编译绑定，然后再测试。」

### 让它能访问 CI、测试、类型与代码检查工具

智能体大部分的「魔法」来自它能修正自己的错误、并针对错误信息反复迭代。通过类型检查器、代码检查工具、单元测试这类工具提供强有力的反馈回路，能极大提升它的表现。可以考虑用带类型的 Python 而不是普通 Python，或用 TypeScript 而不是 JavaScript。教会你的智能体如何运行常用的检查与测试，确保它拥有全部必要的依赖包与访问权限。如果智能体能操作浏览器，就给出运行你前端开发环境的清晰说明。

#### 示例：

我们团队从基本无类型的 Python SDK 全面转向了有类型的 SDK（这本身也是一个很适合交给编码智能体的任务）。

### 发挥你的专业能力

当你熟悉自己的代码库时，上面这一切都会变得更容易。即便是简单任务，也受益于你验证逻辑与结果的能力。**人的监督依然不可或缺**——最终，代码的最终正确性由你负责。即便这些工具变得越来越精密，**所有权与验证仍将是人类工程师的关键职责。**

## 在工作流中使用智能体

![速胜示意图](/agents101/images/quick-wins.png)

一旦你掌握了与智能体对话的基础，就该把这些 AI 助手带进日常工作了。以下是一些把它们变成你日常一部分的实用方式：

### 立刻接住新任务

想象一位同事给你发消息：「嘿，能不能快速把 X 做出来？」或「我们需要调一下 Y」。与其让它打断你的心流，不如直接给自主智能体发一句提示，让它去调查或改。这样你就能继续专注于手头的主要任务。有了一个有意思的副业点子？需要快速做个原型、抓点数据，或复现某项研究？交给你的智能体，之后再回来收货。

#### 示例：

许多团队在 Slack 里讨论 bug 修复或小功能更新时，直接 @Devin。

### 随时随地写代码

设想你正在通勤或出差途中，突然冒出一个紧急 bug，或者你意识到代码里可能留了个错误。别慌！自主智能体通常支持移动端访问，让你能立刻处理这些问题。无论是通过 Slack 的手机应用还是专用的移动应用，许多智能体都能让你在路上解决问题——哪怕 wifi 信号很差。

#### 示例：

拥有这种灵活性，让我们团队在车里和飞机上的产出高了不少。

### 把杂活派出去

卡在二分查找老提交上？还是在新功能写文档？把这些重复性任务交给你的智能体。你会省下宝贵时间，继续专注于更有创造性、更有影响的工作。

#### 示例：

在我们团队，工程师交付一个改动、然后让智能体去更新所有相关文档与面向用户的文案，是很常见的事。

### 跳过选择瘫痪

卡在判断某次重构到底能不能简化代码上？在两个架构方案之间选不出来？**让智能体把两个都实现一遍。**有了具体的例子可比，决策就变得直接，而且丢掉一个方案也不会伤了谁的感情。

#### 示例：

在文本框选型时，我们在 Lexical 与 Slate 之间犹豫，于是让智能体各实现了一版。最终 Slate 胜出，交付的结果更好。

### 配置预览部署

把你的 CI/CD 管线设为在每个新 PR 上自动创建预览部署，给你一个即时可访问的线上 URL。在评审 AI 智能体完成的前端任务时，这尤其方便。

#### 示例：

Vercel 是一个让预览部署变得极简单的部署平台。

## 委派更大的工单

![更大工单的工作流](/agents101/images/larger-tickets-1.png)
![更大工单的工作流](/agents101/images/larger-tickets-2.png)

当拉取请求的规模与复杂度超出几个文件时，一次性处理它们就变得困难。但掌握如何委派**中型到大型**任务（通常是 1–6 小时的工作量），才是自主智能体投资回报最高的地方。省下的不只是几分钟，而是**好几个小时**的产出。小任务可能轻松搞定，但把智能体的能力拉伸到处理更大任务，才能带来最大回报。

### 让智能体产出初稿

对于体量较大的任务，用自主智能体先产出 PR 的初稿，能快速启动进展并大幅削减你的工作量。这里的关键在于提前清楚说明你期望的做法。把自己想象成指导初级开发者的架构师。清楚、详细的说明，能避免你把时间浪费在纠正智能体代码里根本性的误解上。

| 领域 | 出初稿 | 精修 |
|---|---|---|
| 新闻业 | 记者收集初步信息，写出文章初稿 | 编辑审阅稿件、核查事实、润色，最后定稿发表 |
| 餐饮业 | 流水线厨师备料并做出初步菜品 | 副主厨添加调味、调整口味，再送到食客面前 |
| 编码 | 自主智能体根据初步计划开始动手，产出第一版方案 | 人类开发者审阅草稿 PR、给出反馈，并在合并前做人工打磨 |

🛑 记住，大任务还没有（暂时）完全无需人工。对更具挑战性的任务，预期要经过多轮反馈；对打磨抛光，预期需要一些人工调整。现实的目标是**节省约 80% 的时间，而不是完全自动化**——你的专业能力在验证与最终质量保障上依然至关重要。

### 与智能体共同编写 PRD

对于复杂或定义模糊的任务，与自主智能体协作产出一份详细计划会非常有效。一开始你并不了解每个细节或需求，这完全没问题。可以先让智能体去探索一些发现问题，例如「我们的身份认证系统是怎么工作的？」或「哪些服务可能受到影响？」你也可以让智能体指出具体的相关代码位置，供你尽早确认。

某些智能体（例如 Devin 与 Claude Code）提供专门的**规划模式**，专注于阅读和探索现有代码，而不是立刻动手修改。如果你希望在委派任务之前做更充分的准备，[deepwiki.com](http://deepwiki.com)、Devin Search 这类专门的代码库搜索工具能快速给出代码库洞察，帮助简化流程。

### 设置检查点

对于多部分的任务，尤其是涉及多个代码库的，要在过程中设立清晰的检查点：

计划 → 实现一块 → 测试 → 修复 → 检查点评审 → 下一块

在每一重要阶段之后明确要求暂停，尤其是跨多层构建的复杂功能（例如数据库、后端、前端）。用这些检查点来确保实现符合你的预期、澄清疑问（例如「解释一下认证流程并确认其安全性」），并尽早纠正方向，避免问题级联。

#### 示例：

「我要你实现这个功能，它会跨我们的数据库、后端以及多个前端界面。请先规划所需的数据库 schema 变更，做完后告诉我，好让我执行迁移。」→「现在请实现后端改动并加上测试，确保 XYZ 能正常工作。做完告诉我」→「现在在 Web 与移动端两个界面里实现改动，去调用新的后端端点」

### 教会它验证自己的工作

给反馈时，不要只指出问题（「这个函数不工作」）。把**你的测试过程**讲清楚，让智能体能够独立验证未来的任务。对于那些你会反复用到的测试模式，把它们沉淀进智能体的永久知识库（参见「加入智能体的知识库」）。

#### 示例：

在 Devin 里，我们会主动提示用户把关键的测试流程保存进智能体的长期记忆，从而简化未来的交互。

### 在 AI 高改动区域提升测试覆盖率

目前，智能体还不完全具备交互式地把所有场景都测透的能力。在 AI 大量修改的区域提升测试覆盖率，能让你对智能体的产出更有信心。扎实的测试意味着：看起来正确的代码可以放心合并，不必担心。

#### 示例：

在把我们 AI 的 Python 转 C 实现交给它之前，我们团队先加强了代码库中某个关键部分的单元测试。

## 自动化工作流

![工作流自动化](/agents101/images/automating-workflows.png)

智能体响应外部事件的速度远快于人类，而且它们比人类同事**更愿意**做枯燥重复的工作。

### 为你最重复的工作创建快捷方式

工程团队经常遇到重复性、例行的任务。这些正是交给智能体自动化的理想对象。常见例子包括：

- 移除功能开关
- 依赖升级
- 为新功能 PR 修复并补充测试

要高效地搭建这类自动化，通常由一位有经验的工程师创建一份健壮、可复用的提示词模板 [2] 在 Devin 里，这类模板叫 playbook，可以针对这些场景反复运行。，能重复用于这些场景。

#### 示例：

我们的一位客户在开发新功能时，会自动触发三个专门写单元测试的智能体。

### 智能代码评审与规则执行

虽然市面上有专门做快速代码评审的工具 [3] 例如 Greptile 与 CodeRabbit。，但自主智能体也是一个有意思的选项，能给出更准确的洞察——尤其是当它们已经索引过你各仓库的功能之后。

#### 示例：

在 Cognition，我们喜欢维护一份「工程师最常犯错误」清单，并把它提交进代码库。然后，与其编写传统的 lint 规则去捕捉这些错误（这往往做不到），我们让智能体在每个新 PR 上运行，检查是否存在这些错误。

### 接入故障事件与告警

你也可以把自主智能体设为针对特定事件自动触发。例如 Devin 提供了可用的 API，其它智能体则可以通过 CLI 命令集成进自定义工作流。这类配置与 MCP 配合得尤其好，可用于摄取第三方错误日志。

⚠️ 在生产服务的 issue 分级处置上，AI 的调试能力**并不怎么样**。与其让 AI 端到端地修掉冒出来的每个 bug，更实际的做法往往是让 AI 只标出最可疑的错误、改动等等。

## 定制与性能提升

### 环境配置

没有什么比不完整或不匹配的环境更能拖慢智能体。为了让它顺畅运行，请把智能体的环境配置与你的团队**完全对齐**。这包括语言版本、依赖包以及自动化检查。例如，智能体环境里应当安装 pre-commit，而环境配置（密钥、语言版本、虚拟环境、浏览器登录态）应当通过 .envrc 或自定义 .bashrc 之类的工具自动加载。

#### 示例：

我们把智能体的浏览器配置成预认证登录状态，省去了手动认证的麻烦，让测试容易得多。

### 构建自定义 CLI 工具与 MCP

MCP 已广泛可用，把智能体连接到外部工具也很快就能搭起来试用 [4] 在 Devin 里，MCP 仍处于 beta 阶段，我们还在摸索最佳的支撑方式。如需使用请联系我们！。但许多人忽略了为智能体搭建简单的 CLI 脚本。举个简单的例子：你可以给智能体一个脚本，让它根据工单 ID 拉取 Linear 工单的信息。你可能还想给智能体一个工具来可靠地完成工作流中的常见环节，比如一个重启本地开发环境的脚本。

#### 示例：

我们有一位客户在「做一个只暴露测试套件中第一个失败测试的 CLI 工具」上取得了很大成功。这个 CLI 会促使智能体只聚焦那一个测试、并给出详细的错误信息，从而让智能体在长任务上的成功率和完成速度都更高。

### 加入智能体的知识库

如果你的智能体反复犯某些常见错误，那正是把你的反馈固化为智能体知识库的好时机。在 Devin 里有一个专门的知识管理系统。许多产品提供 `.rules` 文件或 `.md` 文件供智能体永久摄取。不要只给它你所使用框架的准则，还要告诉它你项目的整体架构。告诉它不同类型任务常用哪类测试、如何运行重要命令、以及你推荐使用哪些工具。

#### 示例：

我们把自己在「新增服务路由时应遵循的具体流程」教给了智能体。这些信息涵盖了它需要在前端与后端添加样板代码的每一处位置。结果是，这类任务现在可以轻松交给我们的 AI 了。

## 自主智能体的局限

### 调试能力有限

bug 报告有时看起来简单得具有欺骗性。但许多 bug 往往不仅需要访问数据库与日志，还需要超出当今大多数 AI 智能体的调试功力。如果用 AI 辅助调试，我们建议让 AI 给出**可能根因的清单**，而不是让它自己去调试并修好一切。然后由人基于自身经验判断哪一个才是真正的根因。但一旦原因已知，智能体在实现修复上依然能帮上不少忙。

### 细粒度视觉推理能力差

总体而言，当今的模型在**匹配设计稿截图或 Figma 原型所需的细节层级**上，视觉推理能力并不好。它们在那些能用代码层级描述的视觉内容上最可靠（例如把 Figma 里的代码给它）。如果你希望它匹配你的视觉风格，应当使用一套良好、组件可复用的设计系统。

### 知识截止

每当你要使用一个新库，都应当明确把最新文档指给它。否则，由于预训练基础模型存在知识截止，大多数智能体会沿用这些库的旧模式。只要你把文档指给它，一个好的智能体能克服这个问题，但你必须留意这一点（记住，智能体甚至不知道这些库已经有新版本了）。

实践考量

## 管理时间与减少损失

并非每次使用智能体都会成功。在 2025 年，智能体的产出结果确实存在不小的方差。这份工作的一部分，就是学会**以这样的方式使用智能体**：最大化取得好结果的机会，同时把浪费的时间与 Token 降到最低。

### 愿意更早止损

刚开始用智能体的人常犯的一个错误是：即便智能体的工作已经明显跑偏，也执意要把这次交互做成功。如果你发现自己心里冒出「它根本不理我的指令」或「这东西在绕圈子」，那就应当果断中止这次对话，或者自己接手。继续发更多消息，更可能说明你的任务复杂度本就超出了智能体的能力，而不是某个能简单纠正的小失误。

### 让实验多样化

如果你刚接触智能体，我们建议一开始就把注押得分散些。尝试各种不同的提示词与思路。对那些智能体天然表现良好的任务类型加码投入，对那些表现不好的果断止损。不必强求你的智能体每次都取得成功。

### 没有进展时就重新开始

在智能体身上，「推倒重来」是正确的答案，比在人身上频繁得多。如果你给智能体派了任务，而它在处理反馈或纠正方向上挣扎，那么换一个全新的智能体、把所有指令一次性讲清楚，往往能更快取得成功。**智能体修复一个被搞乱的环境的能力，远不如它从零写出干净代码的能力。**

实践考量

## 安全与权限

### 为你的智能体创建账号

一个一次性邮箱对安全地测试各类站点很有帮助。如果智能体需要访问云资源，就为它创建自定义的 IAM 角色。

### 给它一个开发／预发布环境

理想情况下，智能体使用与你团队工程师相同的测试配置。我们建议**完全避免**给它生产服务的访问权限。使用远程智能体时，你可以在它的远程机器上运行完全隔离的测试环境。

### 只读 API 密钥

尽可能只给它只读权限。我们发现，凡是要与外部服务交互的脚本，让人类手动运行仍然更有帮助。

## 前方的巨大变化

我们坚信软件工程师不会消失。即便编码智能体变得更聪明、能力更强，**深厚的技术专长与对你代码库的透彻理解**依然无可替代。对你项目、系统与代码的真正**所有权**，如今比以往任何时候都更关键。在我们团队，工程师被期望同时看护多个系统，同时保持深入的理解与审慎的判断。当自动化放大你的影响力时，并行处理多项任务的能力将不再只是「可行」，而是**必需**。我们很高兴能分享在让自己的组织为这一转变做准备时收集到的洞察，让你和你的团队也能在不断演进的软件开发世界中茁壮成长。
