2　OpenAI 如何使用 Codex

<!-- page 3 -->
引言
Codex 在 OpenAI 的众多技术团队中每天都在使用，包括安全、产品工程、前端、API、基础设施与性能工程等团队。各团队用它来加速一系列工程任务，从理解复杂系统、重构大型代码库，到交付新功能和在高强度截止期下处置故障事件。
基于对 OpenAI 工程师的访谈与内部使用数据，我们整理了这些用例与最佳实践，展示 Codex 如何帮助我们的团队跑得更快、提升工作质量，并在规模上管理复杂度。
3　OpenAI 如何使用 Codex

<!-- page 4 -->
用例 1
代码理解
在入职、调试或调查故障事件时，Codex 帮助我们的团队快速熟悉代码库中不熟悉的部分。
工程师常用 Codex 定位某个功能的核心逻辑、梳理服务或模块之间的关系，并追踪数据在系统中的流转。它还有助于浮现架构模式，或找出那些若靠人工生成需要投入大量精力的缺失文档。
在故障响应期间，Codex 通过揭示组件之间的交互、追踪故障状态如何在系统之间传播，帮助工程师快速进入陌生领域。
来自我们团队的见闻
> 修 bug 时我会用 Ask 模式看看同一个问题还可能出现在代码库的哪些地方。
> ——性能工程师，检索系统

> 值班时我会把调用栈粘贴进去，问 Codex 认证流程在哪里。它会直接跳到正确的文件，让我能快速分级处置。
> ——站点可靠性工程师，API 平台

> 关于代码库的"这个我该在哪做"这类问题，Codex 跨 Terraform 和 Python 的解答比 grep 快得多。
> ——DevOps 工程师，基础设施服务

试着用这些示例提示词让 Codex 做代码理解：
- 这个仓库里的身份认证逻辑实现在哪里？
- 概括请求如何从入口到响应流经这个服务。
- 哪些模块与［模块名］交互，失败又是如何处理的？

用例 2
重构与迁移
Codex 常被用来做跨多个文件或包的改动。例如，当工程师在更新 API、改变某个模式的实现方式，或迁移到新依赖时，Codex 能让改动被一致地应用。
当同一个更新需要应用到几十个文件时，或者当该更新需要对结构和依赖有所察觉、而这又很难用正则或查找替换捕捉时，它尤其有用。
他们还用它做代码清理：拆分过大的模块、用现代模式替换旧模式，或为更好的可测试性做代码准备。
来自我们团队的见闻
> Codex 把我们所有的遗留 `getUserById()` 都换成了新的服务模式，并开好了 PR。它几分钟就做完了原本要花几小时的事。
> ——后端工程师，ChatGPT Web

> 为了扫清发布阻塞项，我让 Codex 扫描旧模式的每一处实例，用 Markdown 总结影响，然后开 PR 提交修复。
> ——产品工程师，ChatGPT Enterprise

试着用这些示例提示词让 Codex 做重构与迁移：
- 按关注点把这个文件拆成独立模块，并为每个模块生成测试。
- 把所有基于回调的数据库访问改写成 async/await。

用例 3
性能优化
Codex 被用来识别并解决性能瓶颈。
在调优或可靠性工作中，工程师会让 Codex 分析缓慢或吃内存的代码路径——例如低效的循环、重复的运算，或代价高昂的查询——并给出优化方案，往往能带来效率与可靠性上的实质提升。
Codex 也被用来维护代码健康度：找出那些仍在活跃使用、但有风险或已废弃的模式。我们的团队依赖它来减少长期技术债，并主动预防回归。
来自我们团队的见闻
> 我用 Codex 扫描重复的高开销数据库调用。它很擅长标出热点路径，并起草我之后可以再调优的批量查询。
> ——基础设施工程师，API 可靠性

> Codex 很擅长快速发现性能问题——我花 5 分钟写提示词，省下了 30 分钟的活。
> ——平台工程师，模型服务

试着用这些示例提示词让 Codex 做性能优化：
- 把这个循环优化到更省内存，并解释你的版本为什么更快。
- 找出这个请求处理函数中重复的高开销操作，并给出缓存机会。
- 为这个函数建议一种更快的数据库批量查询方式。

用例 4
提升测试覆盖率
Codex 帮助工程师更快地写测试——尤其是在覆盖率薄弱或完全缺失的地方。
在做 bug 修复或重构时，工程师常让 Codex 建议覆盖边界情况或可能失败路径的测试。对于新代码，它可以基于函数签名与周边逻辑生成单元测试或集成测试。
在识别边界条件方面，Codex 尤其有帮助，比如空输入、最大长度，或那些不寻常但合法、在初版测试中常被漏掉的状态。
来自我们团队的见闻
> 我把 Codex 指向低覆盖率的模块让它跑一整夜，早上起来就能收到可直接运行的单元测试 PR。
> ——前端工程师，ChatGPT Desktop

> 当切换 monorepo 分支很痛苦时，我会让 Codex 把测试写好并触发 CI，自己继续在分支上干活。
> ——后端工程师，支付与计费

试着用这些示例提示词让 Codex 提升测试覆盖率：
- 为这个函数编写单元测试，包含边界情况与失败路径。
- 为这个排序工具生成一个基于属性的测试（property-based test）。
- 扩展这个测试文件，覆盖围绕空输入与非法状态的缺失场景。

用例 5
提高开发速度
Codex 通过同时加速开发周期的起点与终点，帮助团队跑得更快。
在启动新功能时，工程师用它搭建样板——生成文件夹、模块与 API 桩，从而快速得到可运行的代码，而不必手工把每一块接起来。
当项目临近发布，Codex 通过处理那些较小但必不可少的任务来赶上紧张截止期，例如 bug 分级处置、补齐最后一公里的实现缺口、生成灰度脚本、遥测钩子或配置文件。
它也被用来把产品反馈变成起步代码。工程师常常把用户需求或规格粘贴进去，让 Codex 生成一份粗糙草稿，之后再回来打磨。
来自我们团队的见闻
> 我一整天都在开会，却仍然合并了 4 个 PR，因为 Codex 在后台干活。
> ——产品工程师，ChatGPT Enterprise

> Codex 帮忙把 3–4 个低优先级修复完美地交付了，这些事本来会在待办列表里烂掉，这让人特别有掌控感。
> ——全栈工程师，内部工具

试着用这些示例提示词让 Codex 提高开发速度：
- 为 POST /events 搭建一个新的 API 路由，带基础校验与日志。
- 用这个模板［粘贴你的遥测代码示例］生成一个遥测钩子，用于追踪新引导流程的成功与失败。
- 基于这份规格创建一个桩实现：［粘贴规格或产品反馈］。

用例 6
保持心流
当工程师的日程被切得零碎、充满打断时，Codex 帮他们保持产出。
它被用来记录未完成的工作、把笔记变成可运行的原型，或派生一些之后再回来看的探索性任务。这让暂停与恢复工作变得更容易，不必丢失上下文——尤其在值班或会议缠身的时候。
来自我们团队的见闻
> 如果我顺手发现一个小修复，我会丢一个 Codex 任务出去，而不是去切分支，等有空了再评审它的 PR。
> ——后端工程师，ChatGPT API

> 我经常把 Slack 讨论串、Datadog 追踪、issue 等等转发给 Codex，这样我能专注在高优先级的工作上。
> ——API 工程师，基础设施可观测性

试着用这些示例提示词让 Codex 帮你保持心流：
- 生成一个计划，把这个服务重构并拆成更小的模块。
- 把重试逻辑搭出桩并加一个 TODO——退避逻辑我之后补。
- 总结这个文件，好让我明天能接着上次的进度继续。

用例 7
探索与构思
Codex 对开放式工作也很有用，比如寻找替代方案或验证设计决策。你可以让它给出解决问题的不同思路、探索不熟悉的模式，或对假设做压力测试。这有助于浮现权衡、拓宽设计选项，并磨砺实现上的取舍。
它也被用来找相关联的 bug。给定一个已知问题或已废弃的方法，Codex 可以找出代码中其它地方类似的模式，让抓住回归或完成清理工作变得更容易。
来自我们团队的见闻
> Codex 帮我解决冷启动问题——我粘贴一份规格和文档，它就搭出代码或指出我漏了什么。
> ——产品工程师，ChatGPT Desktop

> 修完一个 bug 后，我会问 Codex 类似的 bug 还可能藏在哪，然后派生出后续任务。
> ——性能工程师，检索系统

试着用这些示例提示词让 Codex 做探索与构思：
- 如果这个系统改成事件驱动而非请求／响应，会怎么实现？
- 找出所有手工拼接 SQL 字符串、而没用我们查询构造器的模块。
- 用更函数式的风格重写这个，避免可变状态与副作用。

最佳实践
当 Codex 获得结构、上下文与迭代空间时，它表现得最好。以下是 OpenAI 各团队正在养成的几个习惯，用来在日常工作中稳定地获得价值。

**用 Ask 模式起步**
对于较大的改动，先用 Ask 模式让 Codex 给出实现计划，然后在切到 Code 模式时，把这份计划作为后续提示词的输入。这个两步流程让 Codex 保持脚踏实地，也有助于避免输出中的错误。Codex 在任务范围界定良好时表现最佳——大约是你或一位同事需要一小时、或几百行代码就能完成的任务。随着模型进步，它能承担的任务规模预期会变大。

**迭代式地改善 Codex 的开发环境**
设置启动脚本、环境变量与网络访问，能显著降低 Codex 的错误率。在跑任务的过程中，留意那些可以通过调整 Codex 环境配置来修正的构建错误。这可能需要几轮迭代，但长期看会带来可观的效率收益。

**像写 GitHub Issue 那样组织你的提示词**
当提示词的写法与你描述 PR 或 issue 中改动的写法一致时，Codex 响应得更好。这意味着在相关时提供文件路径、组件名、diff 和文档片段。用「按［模块 X］里的做法同样实现这个」这类模式来提示，能改善结果。

**把 Codex 的任务队列当作轻量待办列表**
随手丢出任务，用来记录零散想法、半成品工作或顺带发现的小修复。不必有压力要一次产出完整 PR。Codex 很适合当作一个暂存区，等你重新进入专注状态时再回来处理。

最佳实践

**用 AGENTS.md 提供持久上下文**
维护一个 AGENTS.md 文件，帮助 Codex 在你的仓库里跨多次提示更有效地工作。这类文件通常包含命名约定、业务逻辑、已知的怪癖，或 Codex 无法仅凭代码推断出的依赖关系。关于如何组织你的 AGENTS.md 文件，可查阅官方文档。

**借助「Best of N」改善输出**
Best-of-N 功能让你针对单个任务同时生成多个回答，从而快速探索多种方案并挑出最好的那个。对于更复杂的任务，你可以审阅若干轮迭代，并组合不同回答的部分内容，得到更强的结果。

展望
Codex 仍处于研究预览阶段，但它已经在实质性地影响我们的构建方式：帮我们跑得更快、写出更好的代码，并接手那些原本永远不会被排进优先级的工作。
我们对未来的潜力感到兴奋——随着模型变得更好、Codex 更深入地融入我们的工作流，我们期待解锁更多用 AI 开发软件的强大方式。我们会继续分享一路上的所得。
