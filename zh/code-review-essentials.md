代码评审是任何协作式软件项目中不可或缺的一环。大型软件系统通常由不止一个人编写，因此一个高效运转的软件团队需要一套健壮的流程，让成员与代码库本身都朝正确的方向前进。

代码评审是一件强大的工具，它能够：

1. 帮助团队成员在系统变化时同步更新对系统的心智模型
2. 确保改动确实解决了问题
3. 就设计的优劣展开讨论
4. 在 bug 进入生产环境之前抓住它们
5. 保持代码风格与组织结构的一致性

把这些收益理解成一个**需求层次**会很有帮助。

![代码评审：需求层次](/images/code_review_hierarchy.png)

## 让团队成员保持在同一条线上

代码评审最关键的作用，是让团队每一位成员都朝正确的方向前进。你无法安全地修改一个自己并不理解的系统，因此代码评审让团队在认知上保持一致。当 Bob 为账务子系统提交一个拉取请求时，Amy 在评审 Bob 代码的过程中，也同步更新了自己对该系统的心智模型。Amy 有机会对不理解的部分提问，Bob 则从澄清自己的设计决策、并把工作讲给别人听中获益。一个月后当 Amy 需要修改账务子系统时，她对系统的心智模型已经是最新的、随时可用。她花更少时间读代码、在脑子里拼凑系统全貌，而把更多时间用于思考更高层的抽象与设计。每个人都赢了，因为每个人都同步在一起。

## 提交一个合格的拉取请求

在你写下第一行改动系统的代码之前，先问自己这几个问题：

- **「这真的是该做的事吗？」** 客户、团队成员与其他相关方之间永远存在相互竞争的需求。在深入之前先这样问一遍，有助于理清优先级。迭代会、冲刺规划会等其它流程也有助于把这件事保持在正轨上。
- **「团队是否已经认同这个改动是对的？」** 如果没有，最好先通过邮件或当面开启一次设计讨论。当大家在改动之前就对设计达成一致时，你的改动更容易被接受。
- **「我该怎么把这个改动拆成容易评审、容易理解的几块？」** 小改动更容易被思考与理解。团队能快速理解你的改动，好讨论才会随之而来。如果你的改动极其庞大，同事的眼睛会发直，你大概只能收到几条关于风格的吹毛求疵。
- **「我打算怎么测试这个改动，以消灭 bug 并确保正确性？」** 你也许有 QA 部门，但交付能正常工作的优质软件仍然是你作为开发者的职责。易于测试的软件通常耦合更松、切分得更小、也更容易推理。你必须为每一处改动准备测试方案。

我发现，提前回答这些问题，从长远看帮我省掉了许多头疼。最不想遇到的情况是：花几天写完一个改动，结果因为根本性的设计缺陷或团队分歧被否决；或者因为没人能验证其正确性而卡住。再说一遍，目标是**在改动系统的同时让其他团队成员跟上你的改动**。问自己打算如何把工作拆成小块并逐块测试，这在很多方面都有好处：

- 降低风险
- 让改动更容易被推理
- 推动你走向更好的设计

你宁愿用手术刀做许多细小而精准的切口，也不愿用砍刀劈出一道巨大的口子。在大多数增量式的场景里，我偏好手术刀驱动的开发方式，而把砍刀留给该删除大块死代码的时候。

## 发出拉取请求

好，你已经从团队那里获得认可，确认你的改动是好的，也实现了当初设定的设计。那么，**实际发出**拉取请求最有效的方式是什么？你为这些改动辛苦了很久，希望团队其他成员重视你的拉取请求并快速给出反馈。该怎么做？

还记得前面说过，代码评审最重要的部分是保持团队集体心智模型良好对齐吗？你的同事很可能正在忙完全不同的东西，也许在系统的完全不同的部位。他们的大脑处在完全不同的上下文里，所以你必须克服这一点——给他们提供完成评审所需的、有帮助的引导。这意味着要写一份条理清晰的说明：你做了哪些改动、为什么这么做，以及他们只读代码得不到的其它相关信息。别让同事做超出必要的脑力劳动。

我们来看几个拉取请求说明的好例子与坏例子：

坏例子：

```
Title: Fix uninitialized memory bug
Description:

This is the bug Bob and I talked about earlier. I had
trouble with the compiler but managed to make this work. Let me
know what you guys think.
```

如果你是这位拉取请求的作者，请停下来，先把自己放到代码评审者的位置上想一秒。标题含糊，引发的问题比给出的答案还多：内存 bug 在哪？这个改动有多关键？你和 Bob 之前聊的是哪个 bug？你在编译器上遇到了什么麻烦？描述里既没有提供关于问题的有用上下文，也没有对改动的有用说明。如果这个拉取请求很长，评审者就得先扎进代码里、做一番脑力体操来拼凑上下文，才谈得上思考这个改动在整个系统设计中的位置。

下面是一个改进版，它让改动集清楚多了：

```
Title: Fix process crash on startup from uninitialized memory [#54633]
Description:

This bug was causing process crashes on boot due to a memory
initialization error in our statistics Counter class. I talked this
over with Bob, and we both agree the crashes are a rare edge case
that don't warrant a hot-fix release. Here's a summary of the
changes:

  - Moved the underlying int variable into the class initializer
    to prevent ununitialized memory in the Counter.
  - Reworked the Counter interface to simplify caller conditional
    logic and prevent further off-by-one counting problems.
  - Added a unit test that exposes the crash

Testing: I've verified the test suite still passes, and verified
manually that the crash doesn't happen locally.
```

这份拉取请求说明在几处有所改进：标题足够有描述性，能让评审者获得一点简短上下文，并吸引他们点开邮件了解更多。评审者知道这是进程崩溃（通常是相当糟糕的事），而且还有一个 bug 报告编号，如果他想更深入了解这个问题，可以去读该 bug 报告的更多细节。新的描述还指出了问题出在哪里，有助于提供关于这个修复有多关键的上下文。其中有一段摘要列出了拉取请求中高层面的结构性改动，让评审者在看代码之前就先在脑中形成图景。**代码评审者不应该被看到的东西惊到。** 这个例子还说明了做过哪些测试，让评审者确信这些改动经过深思、测试充分、可以合并了。把「点击合并」这件事做得傻瓜式简单，就是为评审者的成功铺路。

## 评审者：给出建设性反馈

评审流程中接下来要考虑的，是给同伴的建设性反馈。如果目标是清晰与对齐，那么高质量的建设性反馈能帮所有人更好地理解系统，并推动代码变得更好。

避免这样说：

- **「这个设计坏了。」** 为什么坏了？怎么才能改得更好？这类说法打击信心，也容易伤人自尊。
- **「我不喜欢这个改动。」** 你为什么不喜欢？你希望改成什么样？不喜欢某样东西没问题，但你应当把自己的想法讲清楚，并给出代码可以如何改进的有用线索。
- **「你能重写成更清楚的版本吗？」** 我现在这个有什么问题？我该怎么重写？哪里不清楚？这类评论本身就不清楚，也没给出简单的改进路径。

换成这样说：

- **「这段代码怎么处理负整数？」** 这类反馈很具体，促使开发者自己去推演结果。作为评审者，你也许已经知道这段代码遇到负整数会崩，但让开发者自己意识到更好。这类问题也可能暗示着测试覆盖的缺口，或者需要对范围做进一步界定。
- **「这一段我看不懂，我不明白为什么 A 类要跟 B 类通信」** 如果开发者没有提供有用的说明，代码结构也不清晰，这类评论有助于推动设计变清晰、代码变干净。
- **「看起来你在这里破坏了一个接口边界。这会怎样影响用户？」** 你指出了自己注意到的疑问，同时给对方善意的假设——他不是故意的。现在他可以想一想破坏接口边界那些看不见的连带影响，然后要么为自己的决定给出理由，要么选择改掉它。

总的来说，**把反馈包装成提问**，是推动清晰与正确性的好方式，同时也帮助开发者在未来改进自己的设计。高质量的创意写作小组通常就是这么互相给反馈的。在创意写作场景里，说「我不喜欢这个角色」是有害的；而同样的话可以更清楚地重述为：「第一章里你的角色温暖而有同情心，现在他变得冷漠如冰。他给我的感觉不像一个真实的人。」这样就有了具体的、可以顺着澄清问题的反馈。

程序员喜欢解决问题、指出毛病，所以天性上就喜欢发现并指出缺陷。很容易把代码评审当成证明自己有多聪明的舞台——通过在同事的代码里找问题。**别这么做。** 代码评审是让更多双眼睛看向一个改动、把关键问题摸出来的方式，但你的目标应当是：在解决当下问题的同时，以一种鼓励团队成员提升技能的方式进行评审。

## 风格问题

大括号位置、变量／函数命名、缩进与空格问题应当处理，但它们**不是**好的代码评审的核心目的（注意我把它们放在了代码评审金字塔的最顶端）。如果你发现团队 90% 的时间都花在纠结缩进和变量名上，那你大概在把大家的时间浪费在本来大部分可以自动化的事情上。写一份风格指南，在提交时强制检查缩进与空格，然后把时间花在价值更高的问题上。我并不是要贬低一致风格的重要性。恰恰相反，拥有一致且符合惯例的风格，是让代码库易读易懂最简单的方式之一。但如果你所有的代码评审都聚焦在这些简单琐碎的任务上，就该问问自己：你是不是在回避那些更难、也更重要的工作——让团队在认知上保持对齐，并思考更高层面的设计。
