简而言之，MCP 为增强 LLM 带来了**可扩展、即插即用的路径**。它让 AI 系统能安全地接入所需的「实时」数据与动作，而每个开发者不必各自重新发明轮子。MCP 的早期采用者已经为 Google Drive、Slack、GitHub、数据库等工具建好了服务器——展示了 AI 智能体如何借助 MCP 与企业内容仓库、DevOps 工具以及其它现实世界系统打交道。

## MCP 架构——一眼看懂它如何工作

### 客户端—服务器结构

MCP 遵循清晰的客户端—服务器架构：

- **MCP 客户端**：嵌入在 AI 应用中（聊天机器人、IDE 助手、自动化智能体）。
- **MCP 服务器**：暴露外部能力，例如函数（工具）、资源（数据）与提示词（模板）。

所有交互都通过标准化的 JSON-RPC 消息发生，维持一种安全、结构化的数据交换：

**JSON-RPC 请求示例：**

例如，要列出可用的工具，MCP 客户端会发出这样的请求：

```
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}
```

服务器会以结构化 JSON 回复，列出各工具（每个都带名称、描述与输入 schema）。例如，某个服务器可能声明一个 get_weather 工具，并描述它需要哪些输入。

```
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": [
    { "name": "get_weather", "description": "Retrieves weather data.", "schema": { "location": "string" } }
  ]
}
```

之后，当 LLM 决定使用某个工具时，客户端就发起调用。MCP 服务器执行该函数，并以结构化 JSON 响应返回结果。宿主应用内的 MCP 客户端随后可以把该结果回填进模型的上下文或响应。实践中，由宿主应用来中介这个过程：它把 LLM 的意图（通常来自模型的函数调用输出）转成 MCP 请求，再把服务器的结构化结果交回 LLM。这种双向交换是**安全且受控的**——模型只能调用服务器所暴露的那些特定工具，所有进出数据都经由既定的协议。
