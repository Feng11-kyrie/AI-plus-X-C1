## 编写高效工具的原则

本节把我们的经验提炼成几条编写高效工具的指导原则。

### 为智能体选择合适的工具

**工具越多，未必结果越好。** 我们观察到的一个常见错误，是工具仅仅把现有的软件功能或 API 端点包一层——不管这些工具是否适合智能体。这是因为智能体相对于传统软件有着不同的「可供性」（affordance）——也就是说，它们感知自己能用这些工具采取哪些潜在行动的方式是**不同的**。

LLM 智能体的「上下文」是有限的（即它们一次能处理的信息量有上限），而计算机内存廉价且充裕。设想在通讯录里查找联系人的任务。传统软件程序可以高效地存储并逐条处理联系人列表，检查完一个再处理下一个。

但如果 LLM 智能体用的工具返回**全部**联系人、然后必须逐 Token 通读一遍，那它就在把有限的上下文空间浪费在无关信息上（想象你翻遍通讯录每一页、从上到下找一个人——也就是暴力搜索）。更好、也更自然的方式（对智能体和人类都一样）是先直接跳到相关的那一页（也许是按字母顺序找到它）。

我们建议围绕少数几个高影响的特定工作流，精心打造少量工具，与你的评估任务相匹配，再由此扩展。在通讯录这个例子里，你可以选择实现 `search_contacts` 或 `message_contact` 工具，而不是 `list_contacts`。

工具可以**合并功能**，在底层处理潜在的多项离散操作（或 API 调用）。例如，工具可以用相关元数据充实响应，或在单次工具调用中处理那些经常被链式组合的多步任务。

以下是一些例子：

- 与其实现 list_users、list_events 和 create_event 三个工具，不如考虑实现一个 schedule_event，它会查找可用时间并安排事件。
- 与其实现 read_logs，不如考虑实现 search_logs，它只返回相关日志行与一些周边上下文。
- 与其实现 get_customer_by_id、list_transactions 和 list_notes，不如实现 get_customer_context，一次性汇总某位客户全部近期且相关的信息。

确保你构建的每个工具都有清晰、独特的用途。工具应当让智能体能够像人类在获得同样底层资源时会做的那样去拆分并解决任务，同时减少那些本会被中间输出消耗掉的上下文。

工具太多或功能重叠，也会让智能体分心、不去追求高效策略。对要构建（以及**不**构建）哪些工具做审慎而有取舍的规划，回报很实在。
