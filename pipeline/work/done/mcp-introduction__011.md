## 早期局限（没有内置身份认证）

MCP 刚出现时（2024 年底），它提供了工具与数据交换的核心协议，但缺少用于连接远程服务器的标准化认证机制。实践中，早期的 MCP 演示与实现往往要求把 MCP 服务器跑在**本地**或受信任的环境中，那里认证不是什么大问题（因为 AI 与服务器跑在同一台机器上）。例如，开发者可以在自己的 [localhost](http://localhost) 上跑一个 Google Drive 的 MCP 服务器，配上一个事先获取的令牌，然后让 AI 应用指向它。但要在互联网上、或与第三方服务一起使用 MCP，没有正式的认证流程就很棘手。

许多早期 MCP 服务器假定用户会在启动时手动把凭据或 API 密钥提供给服务器。举例来说，Anthropic 的快速上手指南建议通过配置或命令行提供你自己的凭据（API 密钥、令牌）来运行预置服务器。这意味着服务器本身能接触到你的密钥，而 MCP 客户端只是信任那个服务器。这对个人或单用户场景可行，但对多用户应用或云端托管的智能体就不太可扩展了。当时没有一套**标准握手**能让 AI 智能体表明：「嘿，我被授权代表用户 X 访问这个服务；这是我的凭据。」

本质上，早期 MCP 客户端除了带外方式（例如预先共享一个令牌，或在无认证状态下运行），没有办法向 MCP 服务器做身份认证。这是一个显著的局限——**MCP 的设计初衷是开放、基于互联网的，但没有认证标准，安全的远程使用就被束缚住了**。

缺少认证标准意味着 **MCP 客户端无法安全地自行连接任意服务器**。你要么把客户端 ID／API 密钥硬编码进客户端（在分布式应用中并不理想），要么只能在没有认证的情况下运行，并假定只有已授权用户能触及该服务器（通常靠把它保持在本地）。显然，要让 MCP 发挥全部潜力（例如以安全方式把 AI 智能体连到云端托管的数据源），需要更好的方案。好消息是社区认识到了这一点，并着手把基于 OAuth 的身份认证内建进 MCP。
