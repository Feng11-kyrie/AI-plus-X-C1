- **自定义集成与 API 密钥管理**：最常见的传统做法是为每个服务写定制代码，并把凭据（API 密钥或令牌）交给 LLM 去使用这些集成。例如，你可能会写一个查询 API 的 Python 函数，把调用该函数的能力给 LLM，并在后端手工管理 API 密钥。这种做法费人力且不可扩展——每新增一个数据源就要写新代码，而每个环境都必须安全地管理 API 密钥。它常常导致系统脆弱，因为每套集成都是独一无二的。相比之下，MCP 把这些交互集中并标准化：AI 智能体只需处理 MCP 这一层，而任何 MCP 服务器（对应任何服务）都能以即插即用的方式工作。新增服务器**完全不需要改动客户端代码**。此外，MCP 为身份认证提供了正式结构（后文讨论），因此把 API 密钥交给 AI 不再是临时起意，而是通过一套安全协议来完成。
- **ChatGPT 插件（OpenAI 插件）**：2023 年，OpenAI 为 ChatGPT 引入了插件系统，让模型能调用由 OpenAPI 规格定义的对外 API。这是走向标准化工具调用的一小步，但它有局限。每个插件本质上都是它自己的小型集成（有自己的 API schema 与认证方式），而且必须逐个构建／托管。只有某些平台（如 ChatGPT 或 Bing Chat）能使用这些插件，因为那是专有方案。插件大多也是一次性调用——模型调用一个 API 拿到信息，没有持久连接或持续交换。MCP 的不同在于它是**开放且通用**的（不绑定于某一个供应商或界面），并支持丰富的双向交互与持续的上下文。可以把 ChatGPT 插件想象成封闭工具箱里的专用工具，而 MCP 是任何开发者或 AI 平台都能使用的开放标准工具包。MCP 标准化的认证（尤其是 OAuth）也意味着，相比 ChatGPT 系统中逐个插件各走一套 OAuth 流程，它能以更统一的方式处理对用户数据的安全访问。总之，ChatGPT 插件展现了为 LLM 标准化 API 访问的价值，而 MCP 更进一步：把它变成开放协议，并在 AI 与服务之间建立起持久的「对话」。
- **LLM 工具框架（LangChain、各类智能体库）**：在 MCP 之前，许多开发者用 LangChain 这类框架给模型配工具。在这些方案里，你定义一组工具函数（带描述）以及智能体的提示词逻辑，让 LLM 决定是否使用它们。这能行得通，但每个工具的幕后仍需要定制实现——LangChain 最终在其库里维护了数百个工具集成。本质上，LangChain 提供的是**面向开发者**的标准（一个 Python 类接口），用于把工具集成进智能体的代码库，但没有为模型提供在运行时动态发现新工具的能力。MCP 与这些框架是互补的，它把标准化转向**面向模型**。有了 MCP，智能体可以发现并使用任何 MCP 服务器提供的工具，即便智能体的代码事先并未显式包含该工具。事实上，LangChain 已加入支持，可以把 MCP 服务器当作又一种工具来源——这意味着用 LangChain 构建的智能体能轻松调用 MCP 工具，从而利用不断壮大的 MCP 服务器生态。区别在于，MCP 把接口通过一套协议（JSON-RPC，带元数据等）正式化，使其更容易接入不同环境，而不只是 Python 框架。类似地，OpenAI 原生的函数调用功能可以看作处理函数调用的**格式**（模型输出一个 JSON 函数调用），而 MCP 以标准化方式处理该调用的**执行**。OpenAI 的函数调用与 MCP 常常协同工作：LLM 产出结构化调用，MCP 客户端／服务器执行它并返回结果，二者合力实现无缝的工具调用。
